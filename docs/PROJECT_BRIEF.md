# PROJECT BRIEF — Second Brain PKB

Точка входа в проект: видение, ключевые принципы, состав частей, фазы и критерии их успеха. Документ задаёт рамку, в которой работают все остальные артефакты — метамодель, ADR, журнал решений и реестры.

## Видение

Личная база знаний, в которой структура не задана заранее жёстко, а описывается той же базой. Пользователь добавляет новый тип объекта, свойство или отношение — и система узнаёт о нём без изменения кода.

## Ключевые принципы

1. **Самоопределение.** Тип — это объект. Свойство — объект. Отношение — объект. Всё имеет `id` и `type`.
2. **Расширяемость без правки плагина.** Новый тип = новая заметка, а не новая версия кода.
3. **Явная семантика.** У каждого объекта есть слой (схема / экземпляр), статус (черновик / принято) и владелец.
4. **Проверяемость.** Правила валидации — тоже объекты; их можно добавлять и отключать.

## Что входит в проект

| Часть | Назначение |
|---|---|
| Метамодель | описание того, как устроены объекты, свойства, отношения, таксономии, фасеты, автоматизации |
| Документация | глоссарий, реестр типов, правила, примеры |
| ADR | зафиксированные архитектурные решения с альтернативами |
| JSON Schema | машиночитаемые артефакты для проверки |
| Плагин Obsidian | реализация метамодели: TypeScript + Obsidian API |
| Примеры | эталонные экземпляры и шаблоны заметок (`examples/`, фаза 3) |

Фаза 1 завершена на уровне документов: метамодель, реестры, ADR-001…ADR-008 и UX-контракты плагина описаны (DL-035). Машиночитаемые артефакты — JSON Schema (`schema/`) и правила валидации как объекты `type: validation-rule` (`docs/validation/`) — перенесены в фазу 2, реализация контрактов — в фазы 4–5 (`plugin/`). Статусы фаз синхронизированы с `docs/project-map/PROJECT_MAP.md`; Q-001 закрыт в iter-008.

Фаза 2 начата в iter-009 (DL-036…DL-039, ADR-009): созданы три схемы JSON Schema 2020-12 (`schema/object.json` — любой объект, `schema/system-definitions.json` — определения `type`, `property`, `relation`, `field-expansion`, `schema/media.json` — обёртка `image` и значения `media` / `list<media>`), реестр и формат правил валидации (`docs/validation/00-validation-rules.md`) и восемь правил первой волны как описания объектов `type: validation-rule` (`docs/validation/01-first-wave-rules.md`). Граница контроля: схема проверяет форму одного объекта (документ из YAML frontmatter), правило — всё, что требует имени файла, другого объекта, множества объектов или вычисления. Q-005 и Q-006 закрыты статусом `ОТКЛОНЕНО`: их триггер «старт фазы 2» не сработал, наборы `enum_values` и реестр свойств ядра схемами первой волны не кодируются.

В iter-010 (DL-040…DL-042) фаза 2 продолжена второй волной: шесть правил валидации — три межобъектные проверки `severity: error` (существование цели канонической ссылки, уникальность машинных ключей `type_value` / `property_key` / `relation_key` / `rule_key`, ацикличность `parent` / `part-of` / `blocks`) и три предупреждения (неактивное развёрнутое поле со значением, глубина `extends` больше пяти, ссылка на объект в `status: deprecated`) — описаны в `docs/validation/02-second-wave-rules.md`. Служебные ключи объекта `validation-rule` зарегистрированы в реестре `docs/metamodel/04-properties.md`, раздел 5, а форма объекта выражена пятой ветвью `oneOf` в `schema/system-definitions.json` (DL-041). Ключ `checks` допускает, кроме `INV-NN`, указатели `DL-NNN` и пункт реестра `<файл>#<раздел>.<пункт>` (DL-040).

В iter-011 (DL-043…DL-045, ADR-010) фаза 2 продолжена второй волной схем: `schema/facet-value.json` (объект `type: facet-value` и обязательный ключ `facet` — одиночная каноническая ссылка) и `schema/core-property-values.json` (15 `$defs` форм значений по каждому из 14 `value_type` плюс `integer-value`, и `properties` двенадцати ключей свойств ядра — частичная схема документа frontmatter). Граница волны: **форма значения — схема, набор значений — реестр** (`enum_values` в схемы не переносятся), сужения формы вводятся только там, где реестр фиксирует ограничение явно (`position` — целое не меньше единицы). Итог фазы 2 на iter-012: **пять схем**, 76 `$ref`, **14 правил** валидации (восемь первой волны и шесть второй), **19 кандидатов** третьей волны; новых правил в iter-011 не добавлялось.

В iter-013 (DL-048) фаза 2 дополнена третьей волной правил — `docs/validation/03-third-wave-rules.md`: пять межобъектных проверок, которые требуют определения отношения, свойства, типа или объекта-цели и потому схемой не выражаются (ADR-009, S1.2). Четыре правила с `severity: error` — `facet-target-is-facet` (цель ключа `facet` является фасетом, INV-15), `relation-endpoints-match` (тип источника и каждой цели значения входит в `source_type` / `target_type` определения с наследованием области по `extends`, INV-17), `relation-cardinality-form` (форма значения по кратности, включая обязательность при `1..1`, INV-17) и `expansion-keys-exist` (определения из `trigger_property`, `adds_properties`, `adds_relations`, `applies_to_type` существуют, INV-25); одно с `severity: warning` — `collection-element-consistent` (род элемента и коллекции: соответствие не является инвариантом модели, `05-core-types.md`, раздел 5, правило 3). Нумерация в реестре сквозная — 15…19, кандидатов осталось 14; новые схемы не добавлялись.

Фаза 3 начата в iter-012 (DL-046, DL-047): создан каталог `examples/` — 13 эталонных заметок (три объекта системного слоя, два объекта слоя классификации, восемь экземпляров слоя наполнения) и `examples/README.md` с таблицами «файл → схема → `rule_key`» и «Объекты вне набора». Набор проверяет схемы и правила на целых заметках: у данных появляется имя файла, второй объект и множество объектов — три класса входа, которых канонические YAML-фрагменты документов не дают. В iter-013 (DL-049) набор расширен шестью заметками медиа и коллекций — `album`, `track`, `film-series`, `film` и две обёртки `image` (обложка альбома, постер фильма): всего 19 эталонных заметок, закрыты все три пары «элемент → коллекция» (`image` → `gallery`, `track` → `album`, `film` → `film-series`), ключ `poster` и отношения `part-of-collection`, `about`, `object-facet-value` у экземпляров ядра. Исполняемого валидатора в репозитории нет: проверки выполнены скриптом песочницы (фазы 4–5).

Фаза 4 начата в iter-014 (DL-050…DL-052): создан каркас плагина `plugin/` — манифест (`id: second-brain-pkb`, версия `0.1.0`, `minAppVersion`), сборка TypeScript в строгом режиме и esbuild в единственный артефакт `main.js` (в git не попадает), точка входа с `onload` / `onunload`, индекс хранилища в памяти (полный проход по заметкам `.md` при загрузке и точечное обновление по событиям хранилища; доступ по `id` и по пути) и стабы двух UX-контрактов — отображаемое имя по `title` (§3) и видимость слоёв с состоянием по умолчанию «`content` и `classification` видимы, `system` скрыт» (§2). В iter-015 (DL-053, DL-054) контракт §3 реализован частично: `title` подменяется в проводнике файлов, заголовке вкладки и заголовке панели листа, подмена включается настройкой «Подменять имя на title» (по умолчанию включена), обратима через атрибуты элемента и обновляется при изменении frontmatter, переименовании файла и изменении раскладки; объект модели без `title` показывается именем файла с пометкой о нарушении INV-07 (§3.5.2). Подмена имени в остальных поверхностях (заголовок заметки, поиск, quick switcher, граф, панели ссылок, предпросмотр) и индикатор совпадения имён (§3.4), фильтрация поиска и графа, создание объектов из пустых ссылок, исполнение правил валидации и bootstrap определений — фаза 5.

## Ограничения

- Плагин: TypeScript, Obsidian API, работа офлайн, без внешних зависимостей без ADR. Ограничение относится к рантайму: dev-зависимости сборки (`plugin/package.json` — esbuild, typescript, типы `obsidian`) в бандл `main.js` не попадают, внешними объявлены `obsidian` и `electron` (DL-052).
- Документация: русский. Код и схемы: английский.
- Один человек пишет в репозиторий; ИИ работают в режиме «чтение / песочница».

## Критерий успеха фазы 1

Метамодель описана так, что по ней **можно** реализовать плагин без дополнительных устных договорённостей: каждый тип, свойство и отношение имеют определение, пример и контракт поведения — в данных и в интерфейсе. Машиночитаемое правило валидации в критерий фазы 1 не входит: оно появляется в фазе 2 (DL-035, уточнение критерия — iter-008).

## Критерий успеха фазы 2

Каждый инвариант (INV-01…INV-27) и каждое реестровое ограничение имеют машиночитаемое выражение: JSON Schema в `schema/` или правило валидации как объект `type: validation-rule` в `docs/validation/`; правило можно добавить и отключить без изменения кода плагина (принцип 4).

Статус на iter-013: критерий выполнен для ядра объекта (INV-01…INV-12), определений системного слоя `type`, `property`, `relation`, `field-expansion` (INV-13, INV-15…INV-22, INV-25), обёртки `image` со значениями `media` / `list<media>` (INV-23, INV-24) и межобъектных ограничений второй волны — существование цели ссылки (INV-15, INV-23), уникальность четырёх машинных ключей (INV-13, INV-16, INV-17), ацикличность графовых отношений, неактивное поле (INV-27), глубина `extends` (INV-18), ссылка на объект в `deprecated` (INV-10). С iter-013 закрыты часть ограничений INV-17 — область отношения и форма значения по кратности, часть INV-15 — тип цели ключа `facet`, и часть INV-25 — существование определений из ключей правила развёртывания; род элемента и коллекции контролируется предупреждением. Форма объекта `validation-rule` выражена схемой, а его состав — реестром правил (DL-041). С iter-011 закрыты значения фасетов (`schema/facet-value.json`) и формы значений свойств ядра по `value_type` для двенадцати ключей из 23 (`schema/core-property-values.json`). Остальное — следующие итерации фазы 2: определения `automation`, перенос одиннадцати ключей свойств ядра и значений отношений в частичную схему, соответствие значения области применения определения (ADR-009, S4 и S6) и четырнадцать кандидатов следующих волн — соответствие значения `applies_to` определения, принадлежность значения `enum_values`, существование файла по пути `attachment`, `format: audiobook` без `attachment` (Q-007), `requires_properties`, матрица коллекций и другие (`docs/validation/00-validation-rules.md`, раздел 7). Вычисления (эффективный набор полей INV-20, INV-26) проверяются алгоритмом плагина в фазах 4–5, а не схемой. С iter-012 состав полей экземпляров слоя наполнения и определения системного слоя проверен на данных: набор `examples/` (фаза 3) покрывает все пять схем, семь из четырнадцати правил — полным или положительным примером, ещё два — частичным и два — формальным; три правила данными набора не покрываются (`relation-acyclic`, `extends-depth`, `deprecated-link-target`), состав покрытия — `examples/README.md`.
