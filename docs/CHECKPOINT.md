## Состояние
Метамодель описана на уровне документов и дополнена механизмом переиспользования наборов полей, моделью изображений и стартовым набором свойств. Три слоя (`system`, `classification`, `content`), девять встроенных метатипов с фиксированными UUIDv7, реестр свойств с парой **key / label**, канонический набор из четырнадцати `value_type` (включая `media` и `list<media>`), четыре отношения классификации и тринадцать отношений ядра (включая `chapter-of` и `part-of-collection`), каноническая форма внутренней ссылки `[[{{type_prefix}}_{{id}}|{{title}}]]`, значения фасетов как объекты `facet-value`, процедура поведения при `status: deprecated`. Наследование типов — одиночное линейное: `extends` (`0..1`, каноническая ссылка), `excludes`, `field_order`, разрешение nearest wins, запрет циклов, детерминированный порядок представления полей. Ядро типов — 29 определений в пяти группах (Знания, Контекст, Медиа, Коллекции, Действия) с пятью цепочками наследования; `image` — обёртка над файлом изображения с обязательным `attachment`; свойства ядра — 15 определений с фиксированными `id`. Инварианты — INV-01…INV-24. Нормативный реестр разделён на `04-properties.md` (свойства) и `06-relations.md` (отношения, ссылки, контракт для плагина); `04-properties-relations.md` удалён (ADR-005, DL-022). Далее — фаза 2: перенос инвариантов и реестров в JSON Schema и правила валидации.

## Открытые хвосты
- **`01-invariants.md` — 296 строк**: достигнута граница R-006 (~300). Следующее добавление инвариантов требует остановки и вопроса о разбиении (варианты — в вопросе 1 REPORT.md iter-005). `05-core-types.md` — 231 строка, `04-properties.md` — 201 строка: запас есть.
- Машиночитаемые артефакты отсутствуют: JSON Schema и правила валидации — фаза 2 (`schema/`, `docs/validation/`). Реестры подготовлены к переносу: `property_key` → имя поля, `value_type` → тип (14 значений), `enum_values` → перечисление, `required` / `applies_to` / `cardinality` → ограничения, `extends` / `excludes` / `field_order` → вычисление эффективного набора полей, `media` → формат ссылки с ограничением цели (`type: image`).
- **Существование файла по пути `attachment` инвариантом не проверяется** (INV-24 фиксирует только обязательность ключа): проверка — кандидат в правила валидации фазы 2.
- **Роли `book` не хранятся полем** (DL-024): роль выводится из состава данных (`attachment`, входящие `chapter-of`), поэтому интерфейс может показать её только как вычисляемую подпись.
- **Свойства пользовательских типов не фиксируются реестром**: реестр свойств ядра (`07-core-properties.md`) покрывает стартовый набор; состав полей типов, создаваемых владельцем, остаётся его решением.
- **Переопределение параметров унаследованного поля на уровне типа не введено** (ADR-004, I3): `value_type`, `required`, `cardinality` едины для всех типов. Ужесточение требования у потомка — отдельным свойством или правилом валидации. Возврат к вопросу при появлении потребности (вопрос 3 REPORT.md iter-004).
- Ядровые типы не имеют фиксированных `id` (DL-019), поэтому документация не может ссылаться на конкретные объекты типов ядра; bootstrap ядра (29 типов, 13 отношений, 15 свойств) — опция плагина (фазы 4–5).
- Отношение «объект → домен» по-прежнему не вводится: домен объекта выводится из `category-domain` его категорий (`06-relations.md`, раздел 2, правило 3).
- Примерные `id` в YAML-примерах (значение фасета из iter-003, экземпляр книги из iter-004, обёртка `image` из iter-005) не являются реестровыми: они совпадают с реестровыми `id` iter-005 только префиксом метки времени (`…-4a28-…`, `…-4a29-…`), полные UUID различны. Коллизий нет, но при чтении примеров это следует учитывать.
