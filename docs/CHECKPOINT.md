## Состояние
Метамодель описана на уровне документов и дополнена механизмом переиспользования наборов полей. Три слоя (`system`, `classification`, `content`), девять встроенных метатипов с фиксированными UUIDv7, реестр базовых свойств с парой **key / label**, канонический набор из двенадцати `value_type`, четыре отношения классификации и одиннадцать отношений ядра, каноническая форма внутренней ссылки `[[{{type_prefix}}_{{id}}|{{title}}]]`, значения фасетов как объекты `facet-value`, процедура поведения при `status: deprecated`. Наследование типов — одиночное линейное: `extends` (`0..1`, каноническая ссылка), `excludes`, `field_order`, разрешение nearest wins, запрет циклов, детерминированный порядок представления полей. Ядро типов — 23 определения в четырёх группах (Знания, Контекст, Медиа, Действия) с пятью цепочками наследования. Инварианты — INV-01…INV-22. Далее — фаза 2: перенос инвариантов и реестров в JSON Schema и правила валидации.

## Открытые хвосты
- Машиночитаемые артефакты отсутствуют: JSON Schema и правила валидации — фаза 2 (`schema/`, `docs/validation/`). Реестры подготовлены к переносу: `property_key` → имя поля, `value_type` → тип (12 значений), `enum_values` → перечисление, `required` / `applies_to` / `cardinality` → ограничения, `extends` / `excludes` / `field_order` → вычисление эффективного набора полей.
- **Свойства ядровых типов не зафиксированы** (`url`, `published`, `isbn`, `due`, `completed` и подобные): в iter-004 зарегистрированы типы и отношения ядра, а свойства создаются пользователем как объекты `type: property`. Реестр свойств ядра — кандидат на отдельную итерацию (вопрос 4 REPORT.md iter-004).
- **Переопределение параметров унаследованного поля на уровне типа не введено** (ADR-004, I3): `value_type`, `required`, `cardinality` едины для всех типов. Ужесточение требования у потомка — отдельным свойством или правилом валидации. Возврат к вопросу при появлении потребности (вопрос 3 REPORT.md iter-004).
