## Что сделано

1. **Цель 1 — `label` / `key` / `title` для системного слоя.** Правило `label` = `title` распространено с определений свойств на все определения системного слоя (типы, свойства, отношения, правила валидации, автоматизации); `key` (`type_value` / `property_key` / `relation_key`) зафиксирован как индикатор в интерфейсе (подпись, бейдж, tooltip), а не как имя; язык — русский `title` / английский `key`; `aliases[1]` определения хранит `key`; исключение для девяти встроенных метатипов сохранено (INV-14). Зафиксировано в ADR-004 (I7), `04-properties-relations.md` (раздел 1.2), INV-22, DL-021, глоссарий (термин Label пересмотрен). Q-002 закрыт по существу.
2. **Цель 2 — наследование типов.** Создан `docs/adr/ADR-004-type-inheritance.md` (182 строки, статус Accepted): `extends` (`0..1`, `value_type: link`, каноническая ссылка, только не-метатипы, ацикличность, cycle-guard, рекомендуемая глубина ≤ 5), `excludes` (список ключей, действие на потомков, отмена через `field_order`, запрет исключать универсальные обязательные свойства), nearest wins, детерминированный порядок представления полей (универсальные → унаследованные от корня к листу → собственные по `field_order`), влияние на `defined_by` / `type_value` / `type` / имя файла / `layer` (идентичность не меняется, `is_a` вычисляется), жизненный цикл предка (`draft` / `accepted` / `deprecated`). Альтернативы: А1 — 6 вариантов (включая «без наследования» и «множественное»), А2 — что наследуется (3), А3 — форма значения `extends` (4). Последствия: 5 положительных, 7 рисков с компенсациями, что фиксируется дополнительно, требования к фазе 2 и плагину.
3. **Цель 2 (продолжение) — инварианты.** В `01-invariants.md` добавлены INV-18 (`extends`), INV-19 (`excludes`), INV-20 (эффективный набор полей, nearest wins, порядок представления, `field_order`), INV-21 (`value_type`), INV-22 (`label` определений системного слоя); INV-12 дополнен правилом «`defined_by` указывает на прямое определение, не на предка», INV-13 — «`type_value` не наследуется», INV-16 — ссылкой на INV-22; обновлены сводная таблица, примечание о нумерации и список кандидатов в правила валидации фазы 2. Объём файла — 275 строк.
4. **Цель 3 — расширенный `value_type`.** В `04-properties-relations.md` добавлен раздел 1.1: 12 канонических значений (`string`, `text`, `number`, `boolean`, `date`, `datetime`, `enum`, `list<string>`, `list<enum>`, `link`, `list<link>`, `uuid`) с формой хранения и примерами; набор объявлен закрытым (новое значение — только через DL); `object` / `json` **не добавлены** с обоснованием (раздел 1.1, правило 1); введён служебный ключ `enum_values` для `enum` / `list<enum>`; зафиксирована неизменяемость `value_type` после `accepted` (INV-21, DL-018).
5. **Цель 4 — ядро типов.** Создан `docs/metamodel/05-core-types.md` (151 строка): статус ядра в модели (обычные объекты `type: type` **без фиксированных `id`**, `type_value` зафиксированы реестром, группа не хранится в данных, «абстрактного типа» нет), четыре обязательные группы — Знания (5 типов), Контекст (6), Медиа (7), Действия (5), всего **23 типа**; для каждого — `type_value`, `label` (ru), назначение, `extends`, типичные отношения ядра, пример; схема всех цепочек и три разобранных цепочки (`source → book` с YAML экземпляра, `event → meeting` с наследованием через группу, `note → claim` с `excludes` и порядком полей); семь правил работы с ядром.
6. **Цель 5 — отношения ядра.** В `04-properties-relations.md` добавлен раздел 10: 11 отношений (`author`, `about`, `part-of`, `participant`, `derived-from`, `supports`, `blocks`, `located-in` + `member-of`, `references`, `contradicts`) с фиксированными `id`, `label` (ru), `source_type`, `target_type`, кратностью `0..*`, обратными направлениями (вычисляются, не хранятся, `relation_key` не занимают) и пятью правилами (ацикличность `part-of` и `blocks`, симметричность `contradicts`, отличие `derived-from` от `references`, расширяемость пользователем).
7. **Фиксированные `id` отношений ядра.** Сгенерированы по документированному правилу (`03-builtin-types.md`, раздел «Как сгенерированы `id`»): итерация `iter-004`, имя `relation:<key>`, смещения 22…32 — продолжение единой последовательности iter-002/iter-003. Проверено скриптом: правило воспроизводит все 22 существующих `id` без расхождений; новые 11 значений — валидные UUIDv7 (версия 7, вариант RFC), уникальны, лексикографически возрастают, не пересекаются с существующими. Параметры генерации iter-004 внесены в `03-builtin-types.md`.

## Отклонения от TASK.md

1. **`excludes` покрывает `relation_key` в дополнение к `property_key`.** В TASK.md (scope, п. 1) сказано «`excludes` (список property_key)». Расширено до обоих видов ключей, потому что значения отношений хранятся в frontmatter под `relation_key` (раздел 4 реестра) и являются такими же полями: без этого потомок не мог бы отказаться от унаследованного отношения (`references` у `claim`, `located-in` у потомка `event`). Варианты — в вопросе 2.
2. **Параметры унаследованного поля не переопределяются на уровне типа.** Nearest wins применяется к принадлежности ключа и его позиции в порядке представления, а не к `value_type` / `required` / `cardinality`: они остаются атрибутами определения свойства или отношения (INV-16, INV-17). Причина: переопределение потребовало бы вложенных структур в frontmatter (`value_type: object` / `list<object>`), которые TASK.md разрешает только при обоснованной необходимости, и второго источника истины о поле. Ограничение зафиксировано в ADR-004 (I3) и INV-20; варианты — в вопросе 3.
3. **`object` / `json` в набор `value_type` не добавлены** (TASK.md допускал их при обосновании). Обоснование отказа — в разделе 1.1 реестра (правило 1) и в DL-018: неструктурированное значение не описывается моделью и не переносится в JSON Schema фазы 2.
4. **Введены два служебных ключа, которых нет в TASK.md:** `field_order` (порядок представления собственных полей — необходим, потому что TASK.md требует зафиксировать «порядок представления унаследованных + собственных полей», а без явного ключа порядок задаётся только правилом по умолчанию) и `enum_values` (без него `enum` / `list<enum>` из расширенного набора `value_type` не машиночитаемы). Оба внесены в раздел 3 реестра как служебные ключи определений, отдельные объекты-определения для них не создавались (соответствует практике iter-003).
5. **Отношений ядра 11, а не 8.** К восьми из TASK.md добавлены `member-of` (person/organization → organization), `references` (упоминание без производности, отличает от `derived-from`) и `contradicts` (симметричная связь утверждений) — в пределах разрешённых «+2–4 по необходимости».
6. **Отношениям ядра выданы фиксированные `id`, типам ядра — нет.** Продолжена практика iter-003 (фиксированные `id` у отношений классификации): `id` нужны для ссылок из документации, правил валидации фазы 2 и bootstrap. Типы ядра — обычные пользовательские определения, их `id` выдаются при создании (иначе ядро нельзя было бы свободно пересоздавать и выводить из эксплуатации). Подтверждение — вопрос 5.

Раздел 10 снабжён указателем из раздела 5.
