## Подтверждение понимания
1. «Эталонные заметки» поняты как целые файлы `.md` с YAML frontmatter и коротким телом, а не как YAML-фрагменты документов: только у целого файла есть имя файла, поэтому на наборе проверяются `filename-matches-object`, `unique-id` и `link-target-exists` на множестве объектов — три класса входа, которых фрагменты не дают (DL-046).
2. «1–2 объекта системного слоя» поняты как ориентир, а не граница: взято три объекта (определение типа `note`, определение свойства `cover`, правило развёртывания). Без них ветви `type-definition`, `property-definition` и `field-expansion-rule` схемы `system-definitions.json` и правила `defined-by-consistent`, `unique-machine-keys`, `trigger-values-subset`, `inactive-field-value` не получили бы данных. Отклонение зафиксировано DL-046 и вынесено вопросом 4.
3. «Без требования реальных bootstrap-id метатипов … если блокирует — согласовать с `defined_by` в комментарии README» выполнено вторым способом: `defined_by` объектов набора указывает реестровые `id` пяти встроенных метатипов (известны из `03-builtin-types.md`), а пять определений типов ядра, которых в наборе нет, перечислены таблицей «Объекты вне набора» в README с `id` и пометкой, что значения иллюстративные (`id` типов ядра реестром не фиксируются, DL-019).
4. «Иллюстративные id не смешивать с реестровыми» выполнено: реестровое значение в наборе одно — определение свойства `cover` (`01a17d3b-4a21-787a-b3db-b9365bb54266`), воспроизводящее канонический пример `07-core-properties.md`, раздел 4; у объектов с выдаваемым `id` значения иллюстративные, а там, где принятая документация уже приводила `id` той же сущности (определения `note` и `image`, книга, персона, обложка, две иллюстрации книги, правило «Профессия → специализация»), они переиспользованы дословно.
