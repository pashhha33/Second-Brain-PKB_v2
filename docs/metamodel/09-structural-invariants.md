# Структурные инварианты

Вторая часть реестра инвариантов: структурные правила системного слоя (INV-13…INV-22), инварианты значений слоя наполнения (INV-23, INV-24) и инварианты развёртывания полей (INV-25…INV-27). Формулировки нормативны; нарушение инварианта означает невалидность объекта.

Сводная таблица INV-01…INV-27, универсальные инварианты (INV-01…INV-12), обязательные свойства объекта и порядок контроля — в [`01-invariants.md`](01-invariants.md); файл выделен из него в iter-006 по R-004 / R-006 ([`../adr/ADR-007-invariants-split.md`](../adr/ADR-007-invariants-split.md), DL-030). Обоснования решений — [`../adr/ADR-003-properties-links.md`](../adr/ADR-003-properties-links.md), [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md), [`../adr/ADR-005-core-extension-and-split.md`](../adr/ADR-005-core-extension-and-split.md), [`../adr/ADR-006-field-expansion.md`](../adr/ADR-006-field-expansion.md).

Машиночитаемое выражение структурных инвариантов — фаза 2 (iter-009, [`../adr/ADR-009-phase2-schemas.md`](../adr/ADR-009-phase2-schemas.md), DL-036…DL-039; iter-010, DL-040…DL-041): форма определений системного слоя — [`../../schema/system-definitions.json`](../../schema/system-definitions.json) (INV-13…INV-22, INV-25; с iter-010 — также форма объекта `type: validation-rule`, пятая ветвь `oneOf`), форма обёртки `image` и значений `media` / `list<media>` — [`../../schema/media.json`](../../schema/media.json) (INV-23, INV-24), обязательные свойства любого объекта — [`../../schema/object.json`](../../schema/object.json). Проверки, требующие других объектов или множества объектов (уникальность `id`, имя файла, `aliases[0] = title`, тип цели `media`, ацикличность `extends`, согласованность `defined_by` и `type_value`, `trigger_values` ⊆ `enum_values`), выражены правилами валидации — [`../validation/00-validation-rules.md`](../validation/00-validation-rules.md), [`../validation/01-first-wave-rules.md`](../validation/01-first-wave-rules.md); межобъектные проверки второй волны (существование цели канонической ссылки INV-15 и INV-23, уникальность машинных ключей INV-13, INV-16, INV-17, ацикличность `parent` / `part-of` / `blocks`) и предупреждения (INV-27, глубина `extends` INV-18, ссылка на объект в `deprecated` INV-10) — [`../validation/02-second-wave-rules.md`](../validation/02-second-wave-rules.md). Формулировки этого файла остаются источником нормы: схема и правило их выражают, а не заменяют; расхождение между ними решается в пользу этого файла и фиксируется DL.

## Структурные инварианты системного слоя

### INV-13 — `type_value` у определений типов

- Объект с `type: type` (определение типа) обязан иметь свойство `type_value` — строку в ASCII kebab-case (INV-04), которую используют в свойстве `type` его экземпляры.
- `type_value` уникален в пределах хранилища: два определения типа с одинаковым `type_value` не допускаются.
- `type_value` неизменяем после перехода определения в `status: accepted`: его изменение меняет тип всех экземпляров и требует перевода определения в `deprecated` и создания нового.
- `type_value` **не наследуется**: у определения типа с `extends` собственное уникальное значение; совпадение `type_value` потомка и предка запрещено (INV-18). Принадлежность предку (`is_a`) в данных не хранится и вычисляется по цепочке `extends`.
- Свойство `title` определения типа может отличаться от `type_value` (например, `title: Иерархическая категория` при `type_value: hierarchical-category`) и изменяемо (INV-07); для определений, создаваемых пользователем и ядром, `title` задаётся на русском и одновременно служит `label` (INV-22).

### INV-14 — встроенные метатипы

- Десять встроенных метатипов ([`03-builtin-types.md`](03-builtin-types.md)) присутствуют в хранилище с момента инициализации и имеют фиксированные `id`, `type`, `type_prefix`, `title` и `aliases` (`aliases[1]` — русское имя).
- Их `status` всегда `accepted`; `layer` всегда `system`; `owner` — `human`.
- Встроенные метатипы не удаляются, не переименовываются и не переводятся в `deprecated`: это ломает самоописание модели и обесценивает `defined_by` существующих объектов.
- Новый встроенный метатип добавляется только через DL с обновлением реестра: в iter-003 добавлен `facet-value` (DL-016), в iter-006 — `field-expansion` (DL-027, DL-029).

### INV-15 — каноническая форма внутренней ссылки

- Внутренняя ссылка на объект имеет форму `[[{{type_prefix}}_{{id}}|{{title}}]]` (DL-015):
  - часть до `|` — имя файла объекта-цели без пути и расширения (INV-06);
  - часть после `|` — значение `title` объекта-цели (INV-07).
- Ссылки вида `[[имя_файла]]` (без alias), `[[title]]` и `[[путь/имя_файла]]` каноническими не являются; плагин нормализует их к канонической форме.
- При изменении `title` цели alias во всех ссылках на неё обновляется; цель ссылки не меняется, так как `id` неизменяем (INV-03).
- Значения отношений хранятся в frontmatter объекта-источника под ключом `relation_key` именно в канонической форме (INV-17, [`06-relations.md`](06-relations.md), разделы 1–2).
- Единственное исключение — `defined_by` (INV-12): хранит UUID строкой.
- Подробно и с альтернативами — [`../adr/ADR-003-properties-links.md`](../adr/ADR-003-properties-links.md).

### INV-16 — `property_key` и `label` у определений свойств

- Объект с `type: property` обязан иметь свойство `property_key` — машинный идентификатор свойства (DL-014): строка в ASCII (`[a-z0-9_]+(-[a-z0-9_]+)*`), уникальная в пределах хранилища, неизменяемая после `accepted`.
- Значение свойства в заметке хранится в frontmatter под ключом, равным `property_key`.
- `label` свойства равен `title` объекта-свойства (INV-07): отдельное поле `label` не вводится.
- `aliases[1]` объекта-свойства равен `property_key` (поиск и по русскому имени, и по машинному ключу).
- Правило `label` = `title` распространяется на все определения системного слоя (INV-22).
- Встроенные свойства и их определения — в [`04-properties.md`](04-properties.md), раздел 4.

### INV-17 — `relation_key` у определений отношений

- Объект с `type: relation` обязан иметь свойство `relation_key` — машинный идентификатор отношения (DL-014): строка в ASCII, уникальная в пределах хранилища, неизменяемая после `accepted`.
- Определение отношения также обязано иметь `source_type`, `target_type` (списки значений `type_value`) и `cardinality` (`0..1`, `1..1`, `0..*`, `1..*`); `inverse_key` — только если обратная связь хранится явно.
- Значение отношения хранится в объекте-источнике под ключом `relation_key` в канонической форме ссылки (INV-15).
- Встроенные отношения классификации — в [`06-relations.md`](06-relations.md), раздел 2.

### INV-18 — `extends`: одиночное линейное наследование

- Определение типа (`type: type`) может иметь ключ `extends` кратности `0..1` — каноническую внутреннюю ссылку (INV-15) на другое определение типа (DL-017).
- Родителем может быть только определение типа, **не являющееся встроенным метатипом** (INV-14): наследование метатипа смешало бы слои (INV-09). Встроенные метатипы `extends` не имеют.
- Наследование определено для определений типов, чьи экземпляры относятся к слою `content`.
- Цепочка `extends` линейна (не более одного родителя) и **ациклична**: тип не может быть собственным предком. Защита — при сохранении определения и правилом валидации фазы 2.
- Рекомендуемая глубина цепочки — до 5 уровней; превышение является предупреждением, а не ошибкой.
- `extends` у определения в `status: accepted` не меняется: смена родителя меняет эффективный набор полей (INV-20) всех экземпляров. Замена — новое определение типа и `deprecated` старого (по образцу INV-13).
- Подробно, с альтернативами и жизненным циклом, — [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md) (I1, I6).

### INV-19 — `excludes`: исключение унаследованных полей

- Ключ `excludes` определения типа — список значений `property_key` и `relation_key`, кратность `0..*` (DL-017).
- Каждый элемент обязан указывать на существующее определение свойства или отношения и фактически входить в наследуемый набор цепочки; «пустое исключение» — предупреждение правила валидации фазы 2.
- Универсальные обязательные свойства (`id`, `type`, `defined_by`, `title`, `aliases`, `layer`, `status`, `owner`) и `type_value` через `excludes` не отменяются: их наличие задано INV-01…INV-13, а не наследованием. Такой ключ в `excludes` — ошибка данных.
- Исключение, объявленное в типе X, действует на X и на всех его потомков; потомок отменяет его явным перечислением ключа в своём `field_order` (INV-20, nearest wins).

### INV-20 — эффективный набор полей и порядок представления

- **Эффективный набор полей** типа — множество ключей свойств и отношений, применимых к его экземплярам: ключ входит в набор, если у определения `applies_to` = `*` либо `applies_to` содержит этот тип или любого его предка по цепочке `extends`, и ключ не исключён по INV-19.
- **Nearest wins:** ключ, объявленный на нескольких уровнях цепочки, входит в набор один раз и принадлежит ближайшему к листу уровню.
- **Порядок представления** детерминирован и одинаков для форм плагина и для JSON Schema фазы 2: (1) универсальные обязательные свойства в порядке номеров реестра; (2) унаследованные поля от корня к листу, внутри уровня — по возрастанию `id` определения; (3) собственные поля в порядке `field_order`, затем неперечисленные в нём — по возрастанию `id` определения.
- `field_order` — список ключей собственных полей типа; допускаются только ключи, входящие в набор цепочки до применения `excludes`. Перечисление несуществующего ключа — ошибка данных.
- Параметры поля (`value_type`, `required`, `cardinality`, `enum_values`, `label`) на уровне типа **не переопределяются**: они остаются атрибутами определения свойства или отношения (INV-16, INV-17, INV-21). Ужесточение требования у потомка выражается отдельным свойством потомка или правилом валидации.

### INV-21 — `value_type` из канонического набора

- `value_type` определения свойства или отношения принимает одно из 14 канонических значений: `string`, `text`, `number`, `boolean`, `date`, `datetime`, `enum`, `list<string>`, `list<enum>`, `link`, `list<link>`, `uuid`, `media`, `list<media>` ([`04-properties.md`](04-properties.md), раздел 2; DL-018, DL-023).
- Набор закрыт: новое значение добавляется только через DL с обновлением реестра. Значения `object` / `json` в набор не входят.
- `enum` и `list<enum>` требуют непустого `enum_values` в определении; `link`, `list<link>`, `media` и `list<media>` хранятся в канонической форме (INV-15); `uuid` — «сырой» UUIDv7 (INV-01); `media` и `list<media>` указывают на обёртку `image` (INV-23).
- `value_type` определения в `status: accepted` неизменяем; замена выполняется новым определением и переводом старого в `deprecated`.

### INV-22 — `label` определений системного слоя

- Для любого определения системного слоя (`type: type`, `property`, `relation`, `validation-rule`, `automation`) **`label` = `title`** (INV-07); отдельное поле `label` не вводится (DL-021).
- `key` определения — `type_value`, `property_key` или `relation_key` — в интерфейсе выступает индикатором (подпись, бейдж, tooltip), а не именем объекта.
- `title` (= `label`) определений, создаваемых пользователем и ядром, задаётся на русском; `key` — английский ASCII (INV-04, INV-16, INV-17); `aliases[1]` определения хранит его `key`.
- Исключение — десять встроенных метатипов: их `title` зафиксирован реестром на английском, русское имя — в `aliases[1]` (INV-14).
- Подробно — [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md) (I7) и [`04-properties.md`](04-properties.md), раздел 3.

## Инварианты значений слоя наполнения

### INV-23 — `media` указывает на обёртку `image`

- Значение свойства с `value_type: media` — каноническая внутренняя ссылка (INV-15) на объект `type: image`; значение с `value_type: list<media>` — список YAML таких ссылок (DL-023).
- Путь к файлу, имя файла и встраивание `![[файл]]` значением `media` не являются: цель ссылки — объект модели с `id`, а не вложение.
- Одна обёртка `image` может быть значением нескольких свойств разных объектов; копирование обёртки для каждой ссылки не требуется.
- Цель ссылки обязана существовать и быть объектом `type: image`; ссылка на объект в `status: deprecated` допустима и остаётся действительной ([`04-properties.md`](04-properties.md), раздел 7).

### INV-24 — обёртка `image` и `attachment`

- Объект `type: image` — обёртка над файлом изображения: он обязан иметь ключ `attachment` (`value_type: string`) с путём к вложению Obsidian относительно хранилища (DL-024).
- Вложение **не является объектом модели**: у файла нет `id`, `type`, `defined_by`, он не участвует в отношениях, не имеет `layer` и не появляется в графе.
- `attachment` допустим и у других типов области применения (`file`, `source`, `note`) — как необязательный: книга в роли «карточка + файл» хранит файл книги ([`05-core-types.md`](05-core-types.md), раздел 4.1).
- Существование файла по пути `attachment` инвариантом не проверяется: это правило валидации фазы 2.

## Инварианты развёртывания полей

### INV-25 — правило развёртывания: состав и ссылки

- Правило развёртывания полей — объект системного слоя `type: field-expansion` (встроенный метатип 10, [`03-builtin-types.md`](03-builtin-types.md)); механизм и примеры — [`08-field-expansion.md`](08-field-expansion.md), решение — [`../adr/ADR-006-field-expansion.md`](../adr/ADR-006-field-expansion.md).
- Обязательные служебные ключи правила: `applies_to_type` (`list<string>`, непустой), `trigger_property` (`string`), `trigger_values` (`list<string>`, непустой), `mode` (`enum`, в v1 единственное значение — `union`); хотя бы один из ключей `adds_properties` / `adds_relations` непустой (DL-027).
- `trigger_property` — `property_key` существующего определения свойства с `value_type: enum` или `list<enum>`; `trigger_values` — непустое подмножество `enum_values` этого определения (INV-16, INV-21).
- Каждый элемент `adds_properties` — `property_key` существующего определения свойства, каждый элемент `adds_relations` — `relation_key` существующего определения отношения; дубликаты внутри списка не допускаются.
- Каждый элемент `applies_to_type` — `type_value` существующего определения типа (INV-13); правило действует на этот тип и на всех его потомков по цепочке `extends` ([`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md), I3).
- `id` правила выдаётся при создании объекта и реестром не фиксируется (по образцу типов ядра, DL-019): состав правил настраивается владельцем, канонические примеры — [`08-field-expansion.md`](08-field-expansion.md), раздел 6.
- Правило в `status: draft` или `deprecated` не применяется к объектам (INV-10; [`04-properties.md`](04-properties.md), раздел 7).

### INV-26 — эффективный набор полей экземпляра с учётом развёртывания

- Эффективный набор полей экземпляра = эффективный набор полей его типа (INV-20) **∪** объединение `adds_properties` и `adds_relations` всех активных правил развёртывания.
- Правило активно для объекта, если одновременно: `status: accepted`; `type` объекта или один из его предков по цепочке `extends` входит в `applies_to_type`; пересечение значения `trigger_property` объекта с `trigger_values` непусто (для `list<enum>` — пересечение списков, для `enum` — вхождение единственного значения).
- Объединение — операция над множествами: идемпотентна и коммутативна, поэтому количество сработавших правил и дубликаты ключей на состав полей не влияют (семантика `mode: union`, DL-028).
- Порядок представления детерминирован: сначала поля эффективного набора типа (INV-20), затем добавленные поля — по возрастанию `id` правил, внутри правила — по порядку перечисления в `adds_properties`, затем в `adds_relations`; `field_order` определения типа переопределяет порядок (nearest wins, INV-20).
- Развёртывание не изменяет параметры определений: `value_type`, `required`, `cardinality`, `applies_to` остаются атрибутами определения свойства или отношения (INV-16, INV-17, INV-21; [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md), I3). Обязательность значения в активном поле выражается правилом валидации фазы 2, а не развёртыванием.
- Наличие в frontmatter значения поля, которое не развёрнуто ни одним активным правилом, не является нарушением инвариантов: такое поле считается неактивным (INV-27).

### INV-27 — смена значения триггера не удаляет данные

- Изменение или удаление значения свойства-триггера не изменяет и не удаляет значения полей, добавленных развёртыванием ранее: данные frontmatter сохраняются (DL-028).
- Поле, добавленное правилом, которое перестало быть активным для объекта, переходит в состояние **неактивного**: интерфейс скрывает его из формы по умолчанию, значение остаётся в заметке.
- Неактивное поле с непустым значением — предупреждение правила валидации фазы 2 («осиротевшее значение»), а не ошибка и не нарушение инварианта.
- Автоматическое удаление значений запрещено; очистка неактивных полей выполняется только явной командой владельца (семантика — [`08-field-expansion.md`](08-field-expansion.md), раздел 7; контракт для плагина — там же, раздел 8, и [`06-relations.md`](06-relations.md), раздел 5, п. 12).
- Возврат значения триггера снова делает правило активным: ранее введённые значения отображаются без повторного ввода.
