# Слои модели: system, classification, content

Метамодель трёхслойна: **системный слой** (`layer: system`) описывает, как устроена модель, **слой классификации** (`layer: classification`) описывает, как объекты группируются, **слой наполнения** (`layer: content`) содержит сами знания. Все три слоя состоят из одних и тех же объектов и подчиняются одним и тем же инвариантам ([`01-invariants.md`](01-invariants.md)); решение о переходе от двух слоёв к трём — [`../adr/ADR-002-three-layers.md`](../adr/ADR-002-three-layers.md), DL-010.

## Зачем три слоя

Двухслойная модель (iter-001: `schema` / `instance`) смешивала две разные роли: определения типов и механизмы классификации. Домен, иерархическая категория и фасет — не типы сущностей и не экземпляры предметной области: они отвечают на вопрос «как объекты сгруппированы», а не «что за объект». Третий слой делает эту роль явной и позволяет:

- отличать расширение модели (новый тип — системный слой) от наведения порядка в знаниях (новая категория — слой классификации);
- задавать разные правила изменения: правка системного слоя затрагивает всю базу, правка классификации — только группировку;
- адресовать классификацию как самостоятельный объект автоматизаций и правил валидации.

## Сравнение слоёв

| Признак | `system` | `classification` | `content` |
|---|---|---|---|
| Назначение | описать, как устроена модель | описать, как объекты группируются | хранить знания предметной области |
| Что содержит | встроенные метатипы, определения типов (включая пользовательские), определения свойств и отношений, правила валидации, автоматизации | домены, узлы иерархических категорий, фасеты и их значения | экземпляры типов: человек, книга, идея, встреча, заметка |
| Возможные значения `type` | `type`, `property`, `relation`, `automation`, `validation-rule` | `domain`, `hierarchical-category`, `facet`, `facet-value` | значения, определённые объектами системного слоя: ядро из 23 типов ([`05-core-types.md`](05-core-types.md)) и пользовательские типы |
| Кто создаёт | автор модели (или bootstrap — для встроенных метатипов) | автор модели при наведении структуры | пользователь при добавлении знаний |
| Пример `title` | `Person` (имя типа), `Validation rule` | `Философия` (домен), `Языки программирования` (категория) | `Иван Петров`, «Преступление и наказание» |
| Пример имени файла | `type_01a17d3b-4de8-70a1-ac3d-4e5f60718293.md` (определение типа `person`) | `domain_01a17d3b-51d0-71b2-bd4e-5f60718293a4.md` | `person_01a17d3b-5d88-74e5-a071-8293a4b5c6d7.md` |
| Влияние правки после `accepted` | затрагивает все объекты этого типа | затрагивает группировку и навигацию | затрагивает один объект |
| Обязательные дополнительные свойства | `type_value` у определений типов (INV-13); `extends`, `excludes`, `field_order` — по необходимости (INV-18…INV-20) | нет | нет |
| Реестр | [`03-builtin-types.md`](03-builtin-types.md), [`04-properties-relations.md`](04-properties-relations.md) | [`04-properties-relations.md`](04-properties-relations.md), разделы 5, 7 | [`05-core-types.md`](05-core-types.md) (ядро, рекомендательно) |

Минимальный набор свойств одинаков для всех трёх слоёв: `id`, `type`, `defined_by`, `title`, `aliases`, `layer`, `status`, `owner` (INV-01…INV-12).

## Системный слой (system)

Назначение — самоописание модели. В слое живут объекты, которые определяют, что может существовать в хранилище:

- **встроенные метатипы** — девять объектов, присутствующих в хранилище изначально; их `id` и `type_prefix` зафиксированы реестром [`03-builtin-types.md`](03-builtin-types.md);
- **определения пользовательских типов и типов ядра** — например, объект с `title: Человек` и `type_value: person`; создание нового типа расширяет модель, поэтому тип принадлежит системному слою, а не слою наполнения. Определения типов могут наследовать друг друга через `extends` (INV-18, [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md)); ядро типов — [`05-core-types.md`](05-core-types.md);
- **определения свойств и отношений** — объекты с `type: property` и `type: relation`; состав ключей и `label` зафиксирован в [`04-properties-relations.md`](04-properties-relations.md);
- **правила валидации и автоматизации** — объекты с `type: validation-rule` и `type: automation`.

Самоописание: значение `type` у объектов системного слоя — один из встроенных метатипов, то есть «тип» описывается объектом типа `type`, «свойство» — объектом типа `property`. Цепочка `defined_by` замыкается на встроенном метатипе `type`, у которого `defined_by` равен собственному `id` (единственная допустимая самоотсылка, INV-12), поэтому бесконечной регрессии нет и внешний реестр «типов типов» не нужен.

```yaml
# системный слой — определение типа, созданное пользователем (корень, без наследования)
id: 01a17d3b-4de8-70a1-ac3d-4e5f60718293
type: type
defined_by: 01a17d3b-4a00-747f-b063-cd02895e0d4f   # встроенный метатип `type`
type_value: person                                    # значение типа для экземпляров (INV-13)
title: Person
aliases:
  - Person
layer: system
status: accepted
owner: human
# имя файла: type_01a17d3b-4de8-70a1-ac3d-4e5f60718293.md
```

```yaml
# системный слой — определение типа-потомка (наследование, ADR-004)
id: 01a17d3b-6a11-7c4d-9e2a-3b5c7d9e1f31
type: type
defined_by: 01a17d3b-4a00-747f-b063-cd02895e0d4f   # встроенный метатип `type`
type_value: book                                      # собственный, не наследуется (INV-13)
extends: "[[type_01a17d3b-6a10-7b2c-8d4e-1a3c5e7f9b20|Источник]]"   # родитель (INV-18)
field_order:                                          # собственные поля в порядке представления (INV-20)
  - isbn
title: Книга                                          # это же значение — label (INV-22)
aliases:
  - Книга
  - book                                              # aliases[1] = type_value (INV-22)
layer: system
status: accepted
owner: human
# имя файла: type_01a17d3b-6a11-7c4d-9e2a-3b5c7d9e1f31.md
```

Наследование не меняет слоёв: и предок, и потомок — объекты системного слоя, а их экземпляры — объекты слоя наполнения. Встроенные метатипы в наследовании не участвуют (INV-18).

## Слой классификации (classification)

Назначение — группировка объектов слоя наполнения по трём независимым механизмам. Состав слоя зафиксирован человеком (TASK.md iter-002) и DL-010: **Domain**, **Hierarchical category**, **Facet**.

### Domain (домен)

- Крупная предметная область, верхний уровень группировки; не иерархичен.
- Объект с `type: domain`; примеры: `Философия`, `Программирование`, `Личные финансы`.
- Домены не перекрываются по смыслу и служат границей для категорий и области видимости для фасетов.

### Hierarchical category (иерархическая категория)

- Узел дерева категорий внутри домена; объект с `type: hierarchical-category`.
- Пример цепочки в домене `Программирование`: `Языки программирования` → `Python` → `Асинхронность`.
- Иерархия задаётся отношением `parent`; принадлежность домену — отношением `category-domain` (кратность `1..1`). Определения — в [`04-properties-relations.md`](04-properties-relations.md), раздел 5.
- Канонический идентификатор — `hierarchical-category`; устаревший термин `taxonomy` сохранён в глоссарии как не рекомендуемый (DL-012).

### Facet (фасет)

- Независимое измерение классификации, которое комбинируется с другими измерениями без построения иерархии; объект с `type: facet`.
- Примеры измерений: `Формат` (статья / книга / видео), `Статус проработки` (сырое / осмысленное / применено), `Год`.
- Фасет не является деревом: значения одного фасета равноправны, объект может иметь значение нескольких фасетов одновременно.

### Facet value (значение фасета)

- Конкретное значение фасета — объект с `type: facet-value` (метатип добавлен в iter-003, DL-016): `Книга` для фасета `Формат`, `2026` для фасета `Год`.
- Объект значения обязан иметь ключ `facet` — каноническую ссылку на объект фасета (кратность `1..1`).
- Привязка знания к значению выполняется отношением `object-facet-value` (кратность `0..*`): значений может быть несколько, в том числе по разным фасетам.
- Отдельные объекты вместо строкового перечисления нужны, чтобы значение можно было переименовать, перевести в `deprecated` и показать в графе (ADR-003, А3).

```yaml
# слой классификации — домен
id: 01a17d3b-51d0-71b2-bd4e-5f60718293a4
type: domain
defined_by: 01a17d3b-4a05-7b2a-a236-1d80c3f98974   # встроенный метатип `domain`
title: Программирование
aliases:
  - Программирование
layer: classification
status: accepted
owner: human
# имя файла: domain_01a17d3b-51d0-71b2-bd4e-5f60718293a4.md
```

```yaml
# слой классификации — узел иерархической категории
id: 01a17d3b-55b8-72c3-8e5f-60718293a4b5
type: hierarchical-category
defined_by: 01a17d3b-4a06-7991-b54e-9352cde369c0   # встроенный метатип `hierarchical-category`
title: Языки программирования
aliases:
  - Языки программирования
layer: classification
status: accepted
owner: human
# имя файла: hierarchical-cat_01a17d3b-55b8-72c3-8e5f-60718293a4b5.md
```

```yaml
# слой классификации — фасет
id: 01a17d3b-59a0-73d4-9f60-718293a4b5c6
type: facet
defined_by: 01a17d3b-4a07-7494-b6d9-328c7108a3c0   # встроенный метатип `facet`
title: Формат
aliases:
  - Формат
layer: classification
status: accepted
owner: human
# имя файла: facet_01a17d3b-59a0-73d4-9f60-718293a4b5c6.md
```

## Слой наполнения (content)

Назначение — собственно знания. Объекты создаются по определениям системного слоя и группируются механизмами слоя классификации. Рекомендуемый стартовый набор типов — ядро из 23 определений в четырёх группах (Знания, Контекст, Медиа, Действия), [`05-core-types.md`](05-core-types.md).

```yaml
# слой наполнения — экземпляр
id: 01a17d3b-5d88-74e5-a071-8293a4b5c6d7
type: person
defined_by: 01a17d3b-4de8-70a1-ac3d-4e5f60718293   # определение типа `person`
title: Иван Петров
aliases:
  - Иван Петров
layer: content
status: accepted
owner: human
# имя файла: person_01a17d3b-5d88-74e5-a071-8293a4b5c6d7.md
```

Связь с классификацией — через отношения `object-category` и `object-facet-value`; домен объекта выводится из домена его категорий (отношение `category-domain`). Определения отношений и форма их хранения — в [`04-properties-relations.md`](04-properties-relations.md), разделы 4–5.

## Связь объекта с его определением

Каждый объект обязан иметь свойство `defined_by` — `id` объекта системного слоя, который его определяет (INV-12):

| Слой объекта | На что указывает `defined_by` |
|---|---|
| `content` | на определение типа (`type: type`) с соответствующим `type_value` |
| `classification` | на встроенный метатип `domain`, `hierarchical-category` или `facet` |
| `system` | на встроенный метатип из [`03-builtin-types.md`](03-builtin-types.md); для самого метатипа `type` — на самого себя (самоотсылка, точка замыкания) |

Согласованность `type` и `defined_by` проверяется правилом валидации (фаза 2): объект, на который указывает `defined_by`, обязан быть определением типа (`type: type`, `layer: system`), а его `type_value` — совпадать со значением `type` объекта (INV-12, INV-13). `defined_by` указывает на прямое определение типа, а не на его предка: принадлежность предку (`is_a`) вычисляется по цепочке `extends` и в данных не хранится (ADR-004, I5).

## Как `type` и имя файла работают на трёх слоях

1. **Правила едины для всех слоёв**: `type` — строка в ASCII kebab-case (INV-04), `type_prefix` вычисляется из `type` по DL-009 (INV-05), имя файла = `{{type_prefix}}_{{id}}` (INV-06). Отдельных правил для системного слоя или классификации нет.
2. **Различие слоёв видно в имени файла только через префикс**: `type_…`, `property_…`, `validation-rule_…` — системный; `domain_…`, `hierarchical-cat_…`, `facet_…` — классификация; `person_…`, `book_…` — наполнение.
3. **Слой не кодируется в имени файла и не выводится из префикса**: `layer` — явное свойство (INV-09); путь (папка) частью идентичности не является.
4. **Уникальность имён файлов** обеспечена единым пространством `id` (INV-02): коллизия между слоями невозможна.
5. **Соответствие слоя и типа проверяемо** (INV-09): `domain`/`hierarchical-category`/`facet`/`facet-value` ⇒ `classification`; встроенные метатипы и определения ⇒ `system`; остальные типы ⇒ `content`.

## Жизненный цикл и статусы

- Путь объекта: `draft` → `accepted` → (при выводе из эксплуатации) `deprecated` (INV-10, DL-011).
- `deprecated` не означает удаление: объект остаётся в хранилище, ссылки на него сохраняются, новые объекты по нему не создаются.
- Определение типа в `draft`: экземпляры считаются черновыми и не используются как основа автоматизаций.
- Определение типа в `deprecated`: существующие экземпляры сохраняются и остаются валидными, новые не создаются; миграция выполняется только созданием новых объектов. Процедура по слоям — [`04-properties-relations.md`](04-properties-relations.md), раздел 8.
- Определение типа-предка в `deprecated`: потомки и их экземпляры остаются валидными, в `deprecated` автоматически не переводятся; плагин помечает цепочку и предупреждает при создании новых экземпляров потомка (ADR-004, I6).
- Вывод встроенного метатипа в `deprecated` не допускается: он ломает самоописание модели.
