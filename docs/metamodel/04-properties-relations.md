# Реестр базовых свойств и отношений

Нормативный реестр свойств и отношений метамодели: для каждого свойства зафиксированы пара **key** (машинный идентификатор) и **label** (человекочитаемое имя для интерфейса), тип значения, обязательность и область применения; для отношений — ключ, источник, цель и кратность. Здесь же зафиксированы канонический набор `value_type`, каноническая форма внутренней ссылки, процедура поведения при `status: deprecated` и отношения ядра.

Слои модели — [`02-layers.md`](02-layers.md); инварианты — [`01-invariants.md`](01-invariants.md); реестр встроенных метатипов — [`03-builtin-types.md`](03-builtin-types.md); ядро типов — [`05-core-types.md`](05-core-types.md); решения — DL-014…DL-016, DL-018, DL-020, DL-021 и [`../adr/ADR-003-properties-links.md`](../adr/ADR-003-properties-links.md), [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md).

## 1. Механика key / label

Свойство модели — объект системного слоя с `type: property`. У каждого свойства обязательны:

| Поле | Назначение | Правило |
|---|---|---|
| `property_key` | машинный идентификатор свойства | ASCII kebab-case или snake_case (`[a-z0-9_]+(-[a-z0-9_]+)*`), уникален в пределах хранилища, неизменяем после `accepted`. Именно этот ключ используется в frontmatter заметок, в JSON Schema (фаза 2) и в правилах валидации |
| `label` | человекочитаемое имя для интерфейса | **`label` = `title` объекта-свойства** (явное правило, отдельное поле не вводится). `title` может содержать кириллицу и пробелы (INV-07), изменяем |
| `aliases` | поиск и быстрый ввод | `aliases[0] = title` (INV-08), `aliases[1] = property_key` — свойство находится и по русскому имени, и по машинному ключу |
| `value_type` | тип значения | одно из 12 канонических значений (раздел 1.1); неизменяем после `accepted` (INV-21) |
| `required` | обязательность | `always` (у всех объектов области применения) или `conditional` (только при условии, описанном в определении) |
| `applies_to` | область применения | `*` (все объекты) либо список значений `type_value`, к которым свойство применимо. Область применения **наследуется**: свойство, объявленное для типа-предка, применимо ко всем его потомкам, кроме исключённых через `excludes` ([`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md), I3) |

Пример объекта-определения свойства (полный):

```yaml
id: 01a17d3b-4a09-79b2-aeb4-446d3725c4c0
type: property
defined_by: 01a17d3b-4a01-73dd-8782-259a7e45663f   # встроенный метатип `property`
property_key: id
title: Идентификатор                                 # это же значение — label
aliases:
  - Идентификатор                                    # aliases[0] = title
  - id                                               # aliases[1] = property_key
value_type: uuid
required: always
applies_to: "*"
layer: system
status: accepted
owner: human
# имя файла: property_01a17d3b-4a09-79b2-aeb4-446d3725c4c0.md
```

Правила:

1. Значение свойства хранится в frontmatter заметки под ключом, равным `property_key`.
2. Смена `label` (`title`) не требует правки данных: ключ остаётся прежним. Смена `property_key` у принятого (`accepted`) свойства не допускается — она потребовала бы переписывания всех заметок.
3. Пользовательское свойство создаётся как новый объект `type: property`; код плагина не меняется (принцип самоопределения).
4. Область применения контролируется правилом валидации: свойство с `applies_to: "*"` обязано быть у каждого объекта; свойство с узкой областью не должно появляться у объектов вне списка и у потомков, исключивших ключ через `excludes`.

### 1.1 Канонический набор `value_type`

Двенадцать значений (DL-018, INV-21). Набор закрыт: новое значение добавляется только через DL с обновлением этой таблицы.

| `value_type` | Хранение в frontmatter | Формат / пример |
|---|---|---|
| `string` | строка YAML | короткое значение: `Иван Петров` |
| `text` | строка или блочный скаляр YAML | многострочный текст без разметки модели |
| `number` | число YAML | `42`, `3.14` (без единиц измерения в значении) |
| `boolean` | `true` / `false` | `true` |
| `date` | строка ISO 8601 | `2026-10-27` |
| `datetime` | строка ISO 8601 со временем и смещением | `2026-10-27T14:30:00+03:00` |
| `enum` | строка из закрытого набора | `draft`; набор — в `enum_values` определения |
| `list<string>` | список YAML строк | `[Иван Петров, Пётр Иванов]` |
| `list<enum>` | список YAML строк из `enum_values` | `[draft, accepted]` |
| `link` | каноническая внутренняя ссылка (INV-15) | `"[[person_01a17d3b-…\|Иван Петров]]"` |
| `list<link>` | список YAML канонических ссылок | значения отношений кратности `0..*` |
| `uuid` | «сырая» строка UUIDv7 (INV-01) | `01a17d3b-4a0b-704c-b84d-181b00576506` |

Правила:

1. **Набор закрыт.** Новое значение `value_type` добавляется только через DL с обновлением таблицы. Значений `object` / `json` в наборе нет: неструктурированный blob не описывается моделью и не переносится в JSON Schema фазы 2 без отдельной схемы; вложенные структуры вводятся отдельным DL при необходимости (ограничение ADR-004, I3).
2. **Форма значения.** `enum` и `list<enum>` обязательны иметь непустой `enum_values` в определении (раздел 3); открытые наборы значений (формат, год, статус проработки) моделируются фасетом и его значениями с `value_type: link` / `list<link>` (раздел 7). `link` и `list<link>` — единственные типы со ссылкой на объект, форма строго каноническая (INV-15, раздел 6). `uuid` — только там, где ссылка нужна машине (`defined_by`, INV-12). Пустое значение свойства — отсутствие ключа в frontmatter, а не пустая строка и не `null`.
3. **Неизменяемость.** `value_type` определения в `status: accepted` неизменяем: смена типа значения ломает существующие заметки. Замена — новое определение и `deprecated` старого (раздел 8.5).

### 1.2 Key / label для всех определений системного слоя

Уточнение DL-014 по решению человека (iter-004, Q-002; ADR-004, I7; DL-021, INV-22):

1. Правило **`label` = `title`** действует для всех определений системного слоя: типов (`type: type`), свойств, отношений, правил валидации, автоматизаций. Отдельное поле `label` не вводится.
2. **`key`** определения — `type_value` (тип), `property_key` (свойство), `relation_key` (отношение). В интерфейсе `key` — **индикатор**: подпись или вторая строка под `label`, бейдж в списках и графе, tooltip. Основное имя в интерфейсе — всегда `label`; `key` как имя не отображается.
3. Язык: `title` (= `label`) определений, создаваемых пользователем и ядром, — русский; `key` — английский ASCII (INV-04, INV-16, INV-17); `aliases[1]` определения хранит его `key`. Исключение — девять встроенных метатипов: их `title` зафиксирован реестром на английском, русское имя хранится в `aliases[1]` (INV-14), правило `label` = `title` для них не меняется.

## 2. Реестр встроенных свойств

Девять встроенных свойств соответствуют инвариантам INV-01…INV-14. `id` записей фиксированы (правило генерации — [`03-builtin-types.md`](03-builtin-types.md), раздел «Как сгенерированы `id`», итерация iter-003).

| № | `property_key` | `label` (= `title`) | `id` определения | `value_type` | `required` | `applies_to` | Инвариант |
|---|---|---|---|---|---|---|---|
| 1 | `id` | Идентификатор | `01a17d3b-4a09-79b2-aeb4-446d3725c4c0` | `uuid` | always | `*` | INV-01…INV-03 |
| 2 | `type` | Тип | `01a17d3b-4a0a-7e27-8774-43162fd59717` | `string` | always | `*` | INV-04 |
| 3 | `defined_by` | Определён типом | `01a17d3b-4a0b-704c-b84d-181b00576506` | `uuid` | always | `*` | INV-12 |
| 4 | `type_value` | Значение типа | `01a17d3b-4a0c-7544-a7fe-586b46636b58` | `string` | always | `type` | INV-13 |
| 5 | `title` | Название | `01a17d3b-4a0d-7bc7-942a-e83c4c85512e` | `string` | always | `*` | INV-07 |
| 6 | `aliases` | Альтернативные имена | `01a17d3b-4a0e-74d6-9f8c-63c27b3f2e0c` | `list<string>` | always | `*` | INV-08 |
| 7 | `layer` | Слой | `01a17d3b-4a0f-7f32-b881-1f1b6cdabfb5` | `enum` (`system`, `classification`, `content`) | always | `*` | INV-09 |
| 8 | `status` | Статус | `01a17d3b-4a10-74b7-b02a-693976c11e88` | `enum` (`draft`, `accepted`, `deprecated`) | always | `*` | INV-10 |
| 9 | `owner` | Владелец | `01a17d3b-4a11-762d-a97d-d75b24a14c42` | `string` | always | `*` | INV-11 |

Имена файлов определений: `property_{{id}}.md` (`type_prefix` для `property` равен `property`, обрезки нет). Значения в скобках у `enum` (записи 7–8) — содержимое `enum_values` соответствующего определения (раздел 1.1, правило 1).

## 3. Служебные ключи определений

Ключи ниже не являются встроенными свойствами объектов: они обязательны для самих определений (`type: property`, `type: relation`, `type: type`). Отдельные объекты-определения для них не создаются — они зафиксированы этой таблицей и будут перенесены в JSON Schema в фазе 2.

| `property_key` | `label` | `value_type` | `required` | `applies_to` | Назначение |
|---|---|---|---|---|---|
| `property_key` | Ключ свойства | `string` | always | `property` | машинный идентификатор свойства |
| `value_type` | Тип значения | `enum` | always | `property`, `relation` | тип значения свойства или ссылки отношения |
| `applies_to` | Область применения | `list<string>` | always | `property` | `*` или список `type_value` |
| `relation_key` | Ключ отношения | `string` | always | `relation` | машинный идентификатор отношения; ключ поля в frontmatter источника |
| `source_type` | Тип источника | `list<string>` | always | `relation` | допустимые `type_value` объекта-источника |
| `target_type` | Тип цели | `list<string>` | always | `relation` | допустимые `type_value` объекта-цели |
| `cardinality` | Кратность | `string` | always | `relation` | `0..1`, `1..1`, `0..*`, `1..*` |
| `inverse_key` | Обратный ключ | `string` | conditional | `relation` | ключ обратного отношения, если оно хранится явно |
| `enum_values` | Допустимые значения | `list<string>` | conditional | `property`, `relation` | непустой набор значений при `value_type: enum` или `list<enum>` (раздел 1.1) |
| `extends` | Наследует типу | `link` | conditional | `type` | каноническая ссылка на родительское определение типа, `0..1`; ацикличность обязательна ([`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md), I1; INV-18) |
| `excludes` | Исключённые поля | `list<string>` | conditional | `type` | ключи (`property_key` / `relation_key`), исключённые у типа и его потомков (ADR-004, I2; INV-19) |
| `field_order` | Порядок полей | `list<string>` | conditional | `type` | порядок представления собственных полей типа; используется и для отмены `excludes` предка (ADR-004, I4; INV-20) |

## 4. Отношения: форма хранения

Отношение — объект системного слоя с `type: relation`. Значение отношения хранится **в объекте-источнике**: в frontmatter под ключом `relation_key`, в канонической форме внутренней ссылки (раздел 6). Множественные значения — список YAML.

```yaml
# фрагмент frontmatter узла иерархической категории
parent: "[[hierarchical-cat_01a17d3b-4a2a-71bf-a98a-2fd4894de046|Языки программирования]]"
category-domain: "[[domain_01a17d3b-51d0-71b2-bd4e-5f60718293a4|Программирование]]"
```

Исключение: `defined_by` хранит «сырой» UUID строкой, а не ссылку (INV-12). Это единственное исключение из канонической формы — ссылка на определение нужна машине для проверки согласованности, а не человеку для навигации.

## 5. Реестр встроенных отношений классификации

| № | `relation_key` | `label` (= `title`) | `id` определения | `source_type` | `target_type` | `cardinality` | `inverse_key` |
|---|---|---|---|---|---|---|---|
| 1 | `parent` | Родительская категория | `01a17d3b-4a12-7667-b7e7-50f350fab871` | `hierarchical-category` | `hierarchical-category` | `0..1` | — (обратное `children` вычисляется плагином, не хранится) |
| 2 | `category-domain` | Домен категории | `01a17d3b-4a13-7dbd-a632-3de3c4bb8200` | `hierarchical-category` | `domain` | `1..1` | — |
| 3 | `object-category` | Категория объекта | `01a17d3b-4a14-7aea-a516-d38c9b49e2ec` | любой тип слоя `content` | `hierarchical-category` | `0..*` | — |
| 4 | `object-facet-value` | Значение фасета | `01a17d3b-4a15-72f2-b5f9-78de0f537bc5` | любой тип слоя `content` | `facet-value` | `0..*` | — |

Правила:

1. **`parent`** задаёт дерево категорий: у корневого узла значение отсутствует (`0..1`). Циклы запрещены — контроль правилом валидации фазы 2.
2. **`category-domain`** обязателен для каждого узла категории (`1..1`): категория без домена не допускается. Все узлы одной ветки принадлежат одному домену (проверяется правилом валидации).
3. **`object-category`** — привязка знания к категории; домен объекта выводится из домена его категорий и отдельным отношением не хранится. Отношение «объект → домен» в iter-003 не вводится: оно избыточно при наличии `category-domain` (см. «Открытые вопросы» REPORT.md).
4. **`object-facet-value`** — привязка знания к значению фасета; значений может быть несколько, в том числе по разным фасетам одновременно.
5. Отношения, не входящие в реестр, создаются пользователем как объекты `type: relation` — код плагина не меняется.
6. Отношения ядра (`author`, `about`, `part-of` и др.) — раздел 10; форма хранения и пример определения те же.

Пример объекта-определения отношения:

```yaml
id: 01a17d3b-4a12-7667-b7e7-50f350fab871
type: relation
defined_by: 01a17d3b-4a02-7576-a16a-764c758b99be   # встроенный метатип `relation`
relation_key: parent
title: Родительская категория                        # это же значение — label
aliases:
  - Родительская категория
  - parent
source_type:
  - hierarchical-category
target_type:
  - hierarchical-category
cardinality: "0..1"
layer: system
status: accepted
owner: human
# имя файла: relation_01a17d3b-4a12-7667-b7e7-50f350fab871.md
```

## 6. Каноническая форма внутренней ссылки

**Инвариант INV-15 (DL-015).** Внутренняя ссылка на объект имеет форму:

```
[[{{type_prefix}}_{{id}}|{{title}}]]
```

- часть до `|` — имя файла объекта-цели без пути и расширения (INV-06);
- часть после `|` — значение `title` объекта-цели (INV-07);
- ссылка без alias (`[[имя_файла]]`) не является канонической; ссылки по `title` (`[[Иван Петров]]`) не являются каноническими.

Правила:

1. Плагин создаёт ссылки только в канонической форме.
2. Плагин нормализует встреченные неканонические ссылки (`[[имя_файла]]`, `[[title]]`, `[[путь/имя_файла]]`) к канонической форме — требование человека (TASK.md iter-003, контекст, п. 1).
3. При изменении `title` объекта-цели плагин обновляет alias во всех ссылках на него; цель ссылки (имя файла) при этом не меняется, так как `id` неизменяем (INV-03).
4. Ссылки на объекты в `status: deprecated` сохраняются и остаются действительными (раздел 8).
5. Единственное исключение — `defined_by`: хранит UUID строкой (раздел 4).

Обоснование выбора и альтернативы — [`../adr/ADR-003-properties-links.md`](../adr/ADR-003-properties-links.md).

## 7. Значения фасетов (`facet-value`)

Значение фасета — объект слоя классификации с `type: facet-value`; метатип добавлен в реестр встроенных метатипов в iter-003 (запись 9, `id` = `01a17d3b-4a08-7875-996d-c4af6179a249`).

- Фасет (`type: facet`) задаёт измерение (`Формат`, `Год`, `Статус проработки`); его значения — отдельные объекты, на которые можно ссылаться, у которых есть `title`, `status` и `aliases`.
- Принадлежность значения фасету хранится в объекте-значении: ключ `facet` (тип значения `link`, область применения `facet-value`, кратность `1..1`), значение — каноническая ссылка на объект фасета.
- Строковое перечисление значений в самом фасете не используется: значения нельзя было бы переводить в `deprecated`, переименовывать без потери связей и отображать в графе.

```yaml
# слой классификации — значение фасета
id: 01a17d3b-4a29-72b4-9a57-be1a133ebf6f
type: facet-value
defined_by: 01a17d3b-4a08-7875-996d-c4af6179a249   # встроенный метатип `facet-value`
facet: "[[facet_01a17d3b-4a28-744e-a519-67031a8e0ae5|Формат]]"      # объект фасета, к которому относится значение
title: Книга
aliases:
  - Книга
layer: classification
status: accepted
owner: human
# имя файла: facet-value_01a17d3b-4a29-72b4-9a57-be1a133ebf6f.md
```

Ключ `facet` относится к слою классификации, поэтому в разделе 3 (служебные ключи определений) его нет:

| `property_key` | `label` | `value_type` | `required` | `applies_to` | кратность |
|---|---|---|---|---|---|
| `facet` | Фасет значения | `link` | always | `facet-value` | `1..1` |

## 8. Поведение при `status: deprecated`

Уточнение семантики DL-011. Правила одинаковы для всех слоёв; различается только область последствий.

### 8.1 Общие правила

1. `deprecated` — не удаление. Файл объекта остаётся в хранилище, `id` неизменяем, ссылки на объект действительны.
2. Объект в `deprecated` помечается в интерфейсе; правила валидации не считают ссылку на него ошибкой.
3. Перевод в `deprecated` обратим: возврат в `accepted` допустим, если не выполнены действия по миграции.
4. Новые объекты не создают по определениям, переведённым в `deprecated`.

### 8.2 Определение типа (`type: type`) в `deprecated`

| Аспект | Поведение |
|---|---|
| Существующие экземпляры | остаются валидными и читаемыми; их `defined_by` продолжает указывать на это определение |
| Создание новых экземпляров | запрещено (плагин не предлагает тип в списках выбора) |
| `type_value` | не переиспользуется: новое определение типа с тем же `type_value` не создаётся (INV-13) |
| Миграция | по решению человека: (а) экземпляры сохраняются как есть; (б) экземпляры переводятся на другой тип — создаётся новый объект с новым `id`, старый переводится в `deprecated` со ссылкой на замену; автоматическая правка `type` и `defined_by` у существующих объектов не выполняется, так как нарушила бы INV-03 в части идентичности и потребовала бы переименования файлов |
| Обязательное действие перед переводом | зафиксировать причину и план по экземплярам в теле заметки определения |

### 8.3 Объект слоя классификации в `deprecated`

- Домен, категория или значение фасета остаются читаемыми и видимыми в навигации с пометкой.
- Новые привязки (`object-category`, `object-facet-value`, `category-domain`, `parent`) к объекту в `deprecated` не предлагаются плагином.
- Существующие привязки сохраняются; замена выполняется человеком или автоматизацией явно.
- Перевод узла категории в `deprecated` не переносит его потомков: дочерние узлы сохраняют `parent`, ветка помечается как устаревшая целиком при навигации.

### 8.4 Встроенные метатипы

Не переводятся в `deprecated` (INV-14): это ломает самоописание модели и обесценивает `defined_by` существующих объектов.

### 8.5 Свойства и отношения в `deprecated`

- Определение свойства или отношения в `deprecated` не удаляет значения из существующих заметок.
- Плагин не предлагает такое свойство при редактировании и не создаёт новые связи по такому отношению.
- Значения устаревшего свойства могут быть перенесены на другое свойство только явной автоматизацией или вручную.

## 9. Контракт для плагина (фазы 4–5)

Требования к реализации, вытекающие из этого реестра. Детали интерфейса — вне scope фазы 1.

1. Создание объекта: генерация UUIDv7, вычисление `type_prefix` (DL-009), формирование имени файла (INV-06), запись обязательных свойств раздела 2, `aliases[0] = title`.
2. Нормализация ссылок к канонической форме (раздел 6) — при сохранении заметки и по явной команде.
3. Отображение свойств в формах по `label` (= `title` определения), редактирование — по `property_key`.
4. Контроль области применения свойств (`applies_to`) и кратности отношений (`cardinality`); сообщения об ошибках — по правилам валидации фазы 2.
5. Bootstrap: создание девяти встроенных метатипов, девяти определений свойств и четырёх определений отношений по фиксированным `id` этого реестра и реестра метатипов.
6. Поведение при `deprecated` — по разделу 8: блокировка создания, пометки в интерфейсе, сохранение ссылок.
7. Если штатный виджет свойств Obsidian не позволяет отобразить `label` и канонические ссылки, плагин предоставляет собственный UI (требование человека, TASK.md iter-003).
8. Наследование: вычисление эффективного набора и порядка полей по цепочке `extends` (ADR-004, I3–I4) — один порядок для форм и для JSON Schema; cycle-guard при сохранении `extends`; предупреждения при глубине цепочки > 5 и при предке в `deprecated`.
9. Интерфейс и ядро: `label` как основное имя с индикатором `key` (раздел 1.2); опциональный bootstrap ядра — 23 определения типов и 11 определений отношений по [`05-core-types.md`](05-core-types.md) и разделу 10, `id` типов ядра выдаются при создании.

## 10. Отношения ядра

Одиннадцать отношений ядра (DL-020) связывают экземпляры типов из [`05-core-types.md`](05-core-types.md). Это обычные объекты `type: relation` с фиксированными `id` (правило генерации — [`03-builtin-types.md`](03-builtin-types.md), итерация iter-004): в отличие от встроенных метатипов они не защищены INV-14 и могут быть переведены владельцем в `deprecated` (раздел 8.5). `source_type` и `target_type` — списки `type_value`; значение `*` означает «любой тип слоя `content`». Область применения наследуется: отношение, объявленное для предка, действует у потомков (ADR-004, I3).

Правила:

1. Форма хранения та же, что у отношений классификации: значение — в frontmatter источника под `relation_key`, канонической ссылкой (разделы 4, 6); пример определения отношения — раздел 5. Обратные направления не хранятся и `relation_key` не занимают: плагин вычисляет их и показывает как подписи входящих связей.
2. `part-of` и `blocks` обязаны быть ацикличными; `contradicts` симметрично (значение хранится только в источнике, плагин показывает его в обе стороны). Кандидаты в правила валидации фазы 2.
3. `derived-from` отличается от `references` производностью: знание получено из цели (цитата из книги), а не просто упоминает её. Отношения вне ядра (`answers`, `owns`, `precedes`) создаются пользователем как объекты `type: relation` — код плагина не меняется.
