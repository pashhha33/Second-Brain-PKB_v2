# Развёртывание полей (field expansion)

Механизм триггерных свойств: значение свойства-триггера определяет, какие дополнительные поля появляются у объекта. Правила развёртывания — объекты системного слоя `type: field-expansion`, а не часть определения типа; механизм не меняет код плагина при добавлении правила.

Решение и альтернативы — [`../adr/ADR-006-field-expansion.md`](../adr/ADR-006-field-expansion.md) (DL-027…DL-029); инварианты — INV-25…INV-27 ([`09-structural-invariants.md`](09-structural-invariants.md)); служебные ключи определений — [`04-properties.md`](04-properties.md), раздел 5; свойства-триггеры и разворачиваемые поля — [`07-core-properties.md`](07-core-properties.md), раздел 1.

## 1. Понятия

| Термин | Определение |
|---|---|
| **Триггерное свойство** | Свойство с `value_type: enum` или `list<enum>`, значение которого сопоставляется с `trigger_values` правил развёртывания |
| **Правило развёртывания** | Объект системного слоя `type: field-expansion`: при каких значениях триггера и у каких типов появляются дополнительные поля |
| **Активное правило** | Правило в `status: accepted`, чей `applies_to_type` покрывает тип объекта (или его предка) и чьи `trigger_values` пересекаются со значением триггера объекта |
| **Развёрнутое поле** | Поле, добавленное в эффективный набор объекта хотя бы одним активным правилом |
| **Неактивное поле** | Поле, значение которого присутствует в frontmatter, но ни одно активное правило его не разворачивает (INV-27) |
| **Эффективный набор полей экземпляра** | Эффективный набор полей типа (INV-20) плюс объединение полей всех активных правил (INV-26) |

Развёртывание дополняет наследование типов, а не заменяет его: `extends` задаёт постоянный состав полей типа, правило развёртывания — состав, зависящий от данных конкретного экземпляра.

## 2. Объект правила развёртывания

Правило — объект системного слоя: `type: field-expansion`, `layer: system`, `defined_by` = `id` встроенного метатипа 10 ([`03-builtin-types.md`](03-builtin-types.md)). `title` правила одновременно служит `label` в интерфейсе (INV-22), `aliases[0] = title` (INV-08).

Служебные ключи правила (полная таблица служебных ключей — [`04-properties.md`](04-properties.md), раздел 5):

| Ключ | `value_type` | `required` | Назначение |
|---|---|---|---|
| `applies_to_type` | `list<string>` | always | `type_value` типов, к которым применяется правило; действует на тип и его потомков по `extends` |
| `trigger_property` | `string` | always | `property_key` свойства-триггера (`enum` или `list<enum>`) |
| `trigger_values` | `list<string>` | always | непустое подмножество `enum_values` триггера; правило срабатывает при совпадении любого значения |
| `adds_properties` | `list<string>` | conditional | `property_key` свойств, добавляемых при срабатывании |
| `adds_relations` | `list<string>` | conditional | `relation_key` отношений, добавляемых при срабатывании |
| `mode` | `enum` | always | режим объединения; в v1 единственное значение — `union` |

Хотя бы один из ключей `adds_properties` / `adds_relations` обязан быть непустым (INV-25): правило, которое ничего не добавляет, недействительно.

```yaml
id: 01a17d3b-7e01-7b42-a6f0-2d5c91e47a38                # иллюстративный id: у правил они не фиксированы
type: field-expansion
defined_by: 01a17d3b-4a32-716d-82a6-503fe47a47a1         # встроенный метатип `field-expansion`
title: Профессия → специализация                          # это же значение — label (INV-22)
aliases:
  - Профессия → специализация                             # aliases[0] = title
  - occupation-specialization
applies_to_type:
  - person
trigger_property: occupation
trigger_values:
  - developer
  - designer
  - researcher
  - teacher
  - writer
adds_properties:
  - specialization
mode: union
layer: system
status: accepted
owner: human
# имя файла: field-expansion_01a17d3b-7e01-7b42-a6f0-2d5c91e47a38.md
```

Правила объекта:

1. **`id` правила не фиксируется реестром** и выдаётся при создании (DL-019 по аналогии с типами ядра): правила настраиваются владельцем, канонические примеры этого файла — образец, а не реестр.
2. **Ссылки в правиле — на ключи, а не на `id`**: `trigger_property`, `adds_properties`, `adds_relations` хранят `property_key` / `relation_key`, `applies_to_type` — `type_value`. Ключи уникальны и неизменяемы после `accepted` (INV-13, INV-16, INV-17), поэтому правило остаётся действительным без пересчёта ссылок.
3. **Все упомянутые определения обязаны существовать** (INV-25): несуществующий ключ делает правило невалидным, а не игнорируемым.
4. **`trigger_values` ⊆ `enum_values`** определения триггера: значение вне набора не сопоставляется никогда и является ошибкой данных правила.
5. **Правило не переопределяет параметры полей**: `value_type`, `required`, `cardinality`, `applies_to` остаются атрибутами определений (INV-26; [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md), I3).
6. **Правило в `draft` или `deprecated` не применяется** (INV-10): перевод в `deprecated` — по [`04-properties.md`](04-properties.md), раздел 7; данные объектов при этом не меняются (INV-27).
7. **Одно свойство может быть триггером нескольких правил**, и одно поле может добавляться несколькими правилами: результат — объединение множеств (раздел 5).

## 3. Свойства-триггеры

1. Триггер — свойство с `value_type: enum` (одиночный выбор) или `list<enum>` (мультивыбор) и непустым `enum_values` в определении ([`04-properties.md`](04-properties.md), раздел 2, правило 2). Сопоставление — точное совпадение строки значения; регистр и пробелы значимы.
2. `enum_values` определения ядра — стартовый набор: владелец вправе расширить его в своём определении, существующие данные при этом не ломаются (`value_type` неизменяем, INV-21; состав значений набора — нет).
3. Триггер может быть любым свойством области применения, не только свойством ядра: правила владельца работают с его собственными определениями свойств.
4. Канонические триггеры ядра (записи 16–18 [`07-core-properties.md`](07-core-properties.md), раздел 1):

| `property_key` | `label` | `value_type` | `applies_to` | `enum_values` (стартовый набор) |
|---|---|---|---|---|
| `occupation` | Профессия | `list<enum>` | `person` | `developer`, `designer`, `researcher`, `teacher`, `writer`, `manager` |
| `format` | Формат издания | `enum` | `book` | `ebook`, `paper`, `audiobook` |
| `creation-method` | Способ создания | `enum` | `image` | `ai-generated`, `photograph`, `scan`, `illustration` |

5. Открытые наборы (профессии, жанры) в модели выражаются фасетом и его значениями ([`04-properties.md`](04-properties.md), раздел 6). Триггер-ссылка на `facet-value` в v1 не поддерживается: значения фасетов не имеют фиксированных `id`, поэтому правило было бы привязано к объектам конкретного хранилища; вариант разобран в [`../adr/ADR-006-field-expansion.md`](../adr/ADR-006-field-expansion.md) (А2).

## 4. Вычисление эффективного набора полей

Порядок вычисления для объекта (INV-26):

1. Вычислить эффективный набор полей типа объекта по цепочке `extends` с учётом `excludes` и nearest wins (INV-20).
2. Отобрать правила: `type: field-expansion`, `status: accepted`, `layer: system`.
3. Для каждого правила проверить соответствие типа: `type` объекта или любой его предок по цепочке `extends` входит в `applies_to_type`.
4. Для каждого подходящего правила проверить триггер: прочитать значение `trigger_property` объекта; для `enum` — значение входит в `trigger_values`, для `list<enum>` — пересечение списка значений с `trigger_values` непусто. Отсутствие значения триггера означает, что правило неактивно.
5. Объединить `adds_properties` и `adds_relations` всех активных правил с набором из шага 1 как множества (дубликаты схлопываются).
6. Упорядочить: сначала поля эффективного набора типа в порядке INV-20, затем добавленные поля — по возрастанию `id` правил, внутри правила — в порядке перечисления `adds_properties`, затем `adds_relations`. `field_order` определения типа переопределяет порядок (nearest wins).

Исключение поля возможно только через `excludes` определения типа (INV-19): правило развёртывания не отменяет поля типа, а добавляет свои. Если добавленное правиломи поле исключено у типа через `excludes`, исключение приоритетнее — поле не появляется.

```yaml
# фрагмент frontmatter экземпляра (person, мультивыбор триггера)
occupation:
  - developer
  - teacher
specialization: Python, архитектура данных, преподавание    # развёрнуто правилом «Профессия → специализация»
member-of: "[[organization_01a17d3b-7e09-8c31-b2d4-6f1a05c47e92|Лаборатория данных]]"
```

## 5. Мультивыбор: `mode: union`

1. Значение триггера типа `list<enum>` может совпасть с `trigger_values` нескольких правил и с несколькими значениями одного правила; результат — **объединение** наборов добавляемых полей (DL-028).
2. Объединение идемпотентно и коммутативно: ни порядок правил, ни количество совпадений на состав полей не влияют. Порядок представления при этом детерминирован (раздел 4, шаг 6).
3. Конфликтов значений не возникает: правило добавляет поле, а не значение; значение поля вводит владелец или автоматизация.
4. Другие режимы (`first-match`, `override`) в v1 не вводятся: значение `mode` остаётся обязательным и принимает единственное значение `union`, новый режим — через DL и обновление [`04-properties.md`](04-properties.md), раздел 5 (`enum_values` ключа `mode`).

## 6. Канонические примеры

`id` правил в примерах иллюстративные: у правил развёртывания фиксированных `id` нет (раздел 2, правило 1). Ключи свойств и отношений — из реестров [`07-core-properties.md`](07-core-properties.md) и [`06-relations.md`](06-relations.md).

### 6.1 `person` + `occupation` (мультивыбор, два правила)

| Правило | `trigger_values` | `adds_properties` | `adds_relations` |
|---|---|---|---|
| Профессия → специализация | `developer`, `designer`, `researcher`, `teacher`, `writer` | `specialization` | — |
| Профессия → место работы | `developer`, `researcher`, `teacher`, `manager` | — | `member-of` |

Персона с `occupation: [developer, teacher]` активирует оба правила: эффективный набор пополняется полем `specialization` и отношением `member-of` (объединение, а не удвоение). Персона только с `occupation: [writer]` получает `specialization`.

```yaml
# правило 2 из пары
id: 01a17d3b-7e02-7a17-9c53-4b6d82f10a75                # иллюстративный id
type: field-expansion
defined_by: 01a17d3b-4a32-716d-82a6-503fe47a47a1
title: Профессия → место работы
aliases:
  - Профессия → место работы
  - occupation-organization
applies_to_type:
  - person
trigger_property: occupation
trigger_values:
  - developer
  - researcher
  - teacher
  - manager
adds_relations:
  - member-of
mode: union
layer: system
status: accepted
owner: human
```

### 6.2 `book` + `format` (одно значение, три правила)

| `format` | `adds_properties` | `adds_relations` | Основание |
|---|---|---|---|
| `paper` | `page-count` | — | объём печатного издания |
| `ebook` | `attachment`, `url` | — | файл книги и внешний адрес |
| `audiobook` | `duration` | `narrator` | длительность и чтец |

```yaml
id: 01a17d3b-7e03-7f26-b1a9-3c7e04d58b61                # иллюстративный id
type: field-expansion
defined_by: 01a17d3b-4a32-716d-82a6-503fe47a47a1
title: Формат «аудиокнига» → длительность и чтец
aliases:
  - Формат «аудиокнига» → длительность и чтец
  - format-audiobook
applies_to_type:
  - book
trigger_property: format
trigger_values:
  - audiobook
adds_properties:
  - duration
adds_relations:
  - narrator
mode: union
layer: system
status: accepted
owner: human
```

`duration` объявлен для `source` и его потомков, включая `book` ([`07-core-properties.md`](07-core-properties.md), раздел 1, запись 9); `narrator` — отношение ядра 14 ([`06-relations.md`](06-relations.md), раздел 3). Роли `book` (раздел 4.1 [`05-core-types.md`](05-core-types.md)) и значение `format` независимы: книга-агрегатор глав тоже может иметь формат.

### 6.3 `image` + `creation-method` (метаданные генерации)

| `creation-method` | `adds_properties` | Основание |
|---|---|---|
| `ai-generated` | `model`, `prompt`, `seed` | воспроизводимость генерации |
| `photograph`, `scan`, `illustration` | — | правил нет: достаточно общих полей обёртки |

```yaml
id: 01a17d3b-7e04-7d39-a07c-5e2b91f63c04                # иллюстративный id
type: field-expansion
defined_by: 01a17d3b-4a32-716d-82a6-503fe47a47a1
title: Способ создания «ИИ-генерация» → метаданные генерации
aliases:
  - Способ создания «ИИ-генерация» → метаданные генерации
  - creation-method-ai
applies_to_type:
  - image
trigger_property: creation-method
trigger_values:
  - ai-generated
adds_properties:
  - model
  - prompt
  - seed
mode: union
layer: system
status: accepted
owner: human
```

Обёртка `image` сохраняет обязательный `attachment` (INV-24) при любом значении `creation-method`: развёртывание добавляет метаданные, но не отменяет поля типа.

## 7. Смена и удаление значения триггера

Принятая семантика — **данные не удаляются** (DL-028, INV-27):

| Сценарий | Состав полей | Значения в frontmatter | Интерфейс |
|---|---|---|---|
| Значение триггера добавлено | поле развёрнуто | вводятся владельцем | поле в форме |
| Значение триггера заменено на другое из набора того же правила | без изменений | сохраняются | без изменений |
| Значение триггера заменено так, что правило стало неактивным | поле неактивно | сохраняются | поле скрыто, предупреждение |
| Значение триггера удалено (ключ отсутствует) | все развёрнутые поля неактивны | сохраняются | поля скрыты, предупреждение |
| Правило переведено в `deprecated` | его поля неактивны у всех объектов | сохраняются | поля скрыты, предупреждение |
| Значение триггера возвращено | поле снова развёрнуто | прежние значения видны | поле в форме |

Обоснование: автоматическое удаление необратимо теряет данные при случайной правке триггера, а сохранение полей как обычных скрывает то, что значение больше не имеет основания. Неактивное поле с непустым значением — предупреждение правила валидации фазы 2, а не ошибка: модель не требует удаления.

## 8. Контракт для плагина

1. Плагин вычисляет эффективный набор полей объекта по разделу 4 при открытии формы, при сохранении и по явной команде пересчёта.
2. Развёрнутые поля отображаются в форме после полей типа; неактивные поля с непустыми значениями показываются в отдельной группе «Не используется» с предупреждением, а не удаляются.
3. Очистка неактивных полей — явная команда владельца с подтверждением; плагин не удаляет значения автоматически (INV-27).
4. Плагин проверяет состав правила при сохранении (INV-25): существование определений по ключам, `trigger_values` ⊆ `enum_values`, непустота хотя бы одного из `adds_properties` / `adds_relations`, `mode: union`.
5. Создание правила — обычный объект системного слоя: код плагина не меняется при добавлении правил (PROJECT_BRIEF, принцип 2).
6. Правила не входят в обязательный bootstrap: канонические примеры создаются по желанию владельца вместе с bootstrap ядра ([`06-relations.md`](06-relations.md), раздел 5, п. 9).
7. Перенос механизма в JSON Schema и правила валидации — фаза 2 (`schema/`, `docs/validation/`): состав полей экземпляра вычислим, поэтому схема типа описывает базовый набор, а развёртывание проверяется отдельным правилом.
