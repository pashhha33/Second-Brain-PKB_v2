# Инварианты объекта

Жёсткие правила, которым обязан удовлетворять любой объект Second Brain PKB — экземпляр, элемент классификации и определение типа. Инвариант нарушен ⇒ объект невалиден; контроль выполняется правилами валидации (фаза 2), здесь зафиксирована только семантика.

Формулировки инвариантов нормативны. Обоснования выбора формата `id`, правила имени файла и производности `type_prefix` — в [`../adr/ADR-001-identity-and-typing.md`](../adr/ADR-001-identity-and-typing.md); обоснование трёхслойной модели и связи объекта с определением — в [`../adr/ADR-002-three-layers.md`](../adr/ADR-002-three-layers.md); обоснование пары key/label и канонической формы ссылки — в [`../adr/ADR-003-properties-links.md`](../adr/ADR-003-properties-links.md); обоснование наследования типов — в [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md); обоснование обёртки изображения, коллекций и `value_type: media` — в [`../adr/ADR-005-core-extension-and-split.md`](../adr/ADR-005-core-extension-and-split.md); обоснование триггерных свойств и правил развёртывания — в [`../adr/ADR-006-field-expansion.md`](../adr/ADR-006-field-expansion.md); разбиение реестра инвариантов — в [`../adr/ADR-007-invariants-split.md`](../adr/ADR-007-invariants-split.md); источники решений — [`../decisions/decision-log.md`](../decisions/decision-log.md) (DL-003, DL-006…DL-039).

В этом файле — сводная таблица INV-01…INV-27, обязательные свойства объекта и универсальные инварианты (INV-01…INV-12). Детальные формулировки структурных инвариантов (INV-13…INV-27) — во второй части реестра: [`09-structural-invariants.md`](09-structural-invariants.md) (выделена в iter-006 по R-004 / R-006, ADR-007).

## Обязательные свойства объекта

Минимальный набор свойств любого объекта (детали — в INV-01…INV-12):

```yaml
id: 01a17d3b-5d88-74e5-a071-8293a4b5c6d7              # UUIDv7, string
type: person                                            # string, ASCII kebab-case
defined_by: 01a17d3b-4de8-70a1-ac3d-4e5f60718293       # id определения типа (system)
title: Иван Петров                                      # string, непустой
aliases:
  - Иван Петров                                         # aliases[0] === title
layer: content                                          # system | classification | content
status: accepted                                        # draft | accepted | deprecated
owner: human                                            # string, непустой
```

Имя файла этого объекта: `person_01a17d3b-5d88-74e5-a071-8293a4b5c6d7.md`.

## Универсальные инварианты

### INV-01 — формат `id`

- Каждый объект имеет свойство `id` типа string.
- Значение — **UUIDv7** (RFC 9562): версия `7`, вариант RFC (`8`, `9`, `a` или `b`).
- Хранится в канонической форме: 36 символов, строчные шестнадцатеричные цифры, дефисы на позициях 9, 14, 19, 24 (индексация с 1). Пример: `01a17d3b-5d88-74e5-a071-8293a4b5c6d7`.
- Другие форматы `id` (ULID, UUIDv4, числовые счётчики, «человеческие» slug-идентификаторы) не допускаются — один формат на всю модель.
- Следствие: лексикографическая сортировка канонических строк `id` совпадает с хронологией их выдачи.

### INV-02 — уникальность `id`

- Область уникальности — **всё хранилище (vault)**, включая объекты системного слоя. Пространство `id` единое, разделения по слоям нет.
- Два объекта с одинаковым `id` — ошибка данных, а не слияние.
- Уникальность контролируется правилами валидации фазы 2; до их появления — проверкой при создании объекта.

### INV-03 — неизменяемость `id`

- `id` выдаётся один раз — при создании объекта — и **никогда не меняется**: ни при переименовании файла, ни при смене `title`, ни при изменении `type`, ни при переносе объекта в другую папку.
- Фиксированные `id` встроенных метатипов ([`03-builtin-types.md`](03-builtin-types.md)) неизменяемы в той же мере: их замена равносильна замене модели.
- Объект, которому требуется другая идентичность, создаётся заново (новый `id`), а старый переводится в `status: deprecated` (INV-10).
- `id` — единственная стабильная основа ссылок, включая `defined_by` (INV-12); всё, что может меняться (`title`, имя файла, путь), стабильным не считается.

### INV-04 — `type`

- Каждый объект имеет свойство `type` типа string — тип сущности (DL-003, DL-007).
- Значение непустое, в **ASCII kebab-case**: `[a-z0-9]+(-[a-z0-9]+)*`, без пробелов, подчёркиваний и не-ASCII символов. Человекочитаемое имя типа хранится в `title` объекта-типа, а не в значении `type`.
- `type` согласован с `defined_by` (INV-12): объект, на который указывает `defined_by`, обязан быть определением типа с `type_value`, равным значению `type`.
- Множество допустимых значений `type` открыто: десять встроенных метатипов ([`03-builtin-types.md`](03-builtin-types.md)) плюс любые пользовательские типы, созданные как объекты системного слоя.
- После перехода объекта в `status: accepted` смена `type` **не рекомендуется**; при необходимости смены типа создаётся новый объект (см. «Последствия» в ADR-001).

### INV-05 — `type_prefix`

- `type_prefix` — короткий префикс имени файла, **производный** от значения `type` (DL-007): он не задаётся вручную независимо от `type` и не хранится как независимый источник истины.
- Правило вычисления (DL-009, статус Accepted; ADR-001, R3):
  1. привести `type` к нижнему регистру (по INV-04 уже в нижнем);
  2. заменить последовательности разделителей (пробел, `_`, `.`, `/`) одним дефисом;
  3. удалить все символы, кроме `[a-z0-9-]`;
  4. удалить дефисы в начале и в конце строки;
  5. если длина результата больше 16 символов — обрезать до 16 и удалить дефис в конце строки;
  6. если результат пуст — объект невалиден (тип обязан давать непустой префикс; не-ASCII имена типов запрещены INV-04).
- Примеры (для значений `type`, удовлетворяющих INV-04): `person` → `person`; `literature-note` → `literature-note` (15 символов, без обрезки); `hierarchical-category` → `hierarchical-cat` (обрезка до 16); `book-2` → `book-2`.
- Шаги 1–3 для корректного `type` тождественны и нужны как защита от ручных правок значения (например, `Literature Note` → `literature-note`).
- Коллизия префиксов у двух разных типов (например, после обрезки) фиксируется переименованием одного из типов до его перехода в `accepted`; механизма ручных переопределений префикса в фазе 1 нет.

### INV-06 — имя файла

- Имя файла заметки: **`{{type_prefix}}_{{id}}`** плюс расширение формата хранения (для Obsidian — `.md`). Разделитель префикса и `id` — одно подчёркивание.
- Пример: `person_01a17d3b-5d88-74e5-a071-8293a4b5c6d7.md`.
- Имя файла уникально в пределах хранилища как следствие INV-02 (уникальность `id`); путь (папка) частью идентичности не является и может меняться.
- Имя файла не содержит символов, запрещённых в именах файлов Obsidian и распространённых ОС: допустимы только `[a-z0-9-]` (префикс), `_` (разделитель), `[0-9a-f-]` (`id`) и `.` перед расширением.
- `id` в имени файла обязан совпадать со значением свойства `id`; `type_prefix` — с префиксом, вычисленным из `type`. Расхождение — признак ручной правки и ошибка данных (контроль — фаза 2).
- Переименование файла не меняет `id`. Переименование файла требуется только в одном случае: изменился `type` объекта (не рекомендуется после `accepted`).

### INV-07 — `title`

- Каждый объект имеет обязательное свойство `title` типа string — читаемое имя сущности (DL-008).
- Значение непустое после удаления пробелов по краям; может содержать любые символы, включая кириллицу и пробелы.
- `title` изменяем: смена `title` не меняет ни `id`, ни имя файла, ни `type_value` определения типа (INV-13).
- `title` — единственное свойство, которое показывается пользователю как имя объекта в списках, графе и результатах поиска.

### INV-08 — `aliases[0] = title`

- Свойство `aliases` — непустой список строк; его **первый элемент всегда равен значению `title`** (точное совпадение строки после удаления пробелов по краям).
- Инвариант действует постоянно: при создании объекта и при любом изменении `title` значение `aliases[0]` синхронизируется с ним.
- Назначение: ссылки вида `[[title]]` и поиск по имени работают без обращения к `id`; дублирование делает имя объекта видимым для механизмов Obsidian, работающих с `aliases`.
- Элементы `aliases[1..]` — произвольные дополнительные имена; ограничений на их состав в фазе 1 нет.

### INV-09 — `layer`

- Каждый объект имеет свойство `layer` с одним из трёх значений (DL-010, DL-012):
  - `system` — описывает, как устроена модель: встроенные метатипы, определения типов (включая пользовательские), определения свойств и отношений, правила валидации, автоматизации;
  - `classification` — описывает, как объекты группируются: домены, узлы иерархических категорий, фасеты и значения фасетов;
  - `content` — знания предметной области: экземпляры пользовательских типов.
- Значение `layer` согласовано со значением `type`:
  - `type` ∈ {`domain`, `hierarchical-category`, `facet`, `facet-value`} ⇒ `layer: classification`;
  - `type` ∈ {`type`, `property`, `relation`, `automation`, `validation-rule`} ⇒ `layer: system`;
  - прочие значения `type` ⇒ `layer: content`.
- Расхождение `layer` и `type` — ошибка данных (правило валидации фазы 2).
- Слой не выводится из имени файла и не кодируется в пути: `layer` — явное свойство (ADR-002, А1).
- Подробно — [`02-layers.md`](02-layers.md).

### INV-10 — `status`

- Каждый объект имеет свойство `status` с одним из значений: `draft`, `accepted`, `deprecated` (DL-011).
- Семантика:
  - `draft` — объект может меняться свободно; экземпляры типа в `draft` считаются черновыми и не используются как основа автоматизаций;
  - `accepted` — объект стабилен; действуют ограничения на смену `type` (INV-04) и на изменение определений системного слоя;
  - `deprecated` — объект выведен из эксплуатации: он сохранён, ссылки на него действительны, новые объекты по нему не создаются.
- Ограничения: встроенные метатипы не переводятся в `deprecated` (INV-14); перевод определения типа в `deprecated` требует решения о судьбе его экземпляров; `deprecated` не означает удаление файла.
- Расширение набора значений — через DL и обновление этого файла.

### INV-11 — `owner`

- Каждый объект имеет свойство `owner` типа string — ответственного за объект (человек или процесс).
- Значение непустое. В персональной базе знаний по умолчанию `human`.
- `owner` не участвует в формировании имени файла и не является ссылкой на объект в фазе 1.

### INV-12 — `defined_by`: связь объекта с определением

- Каждый объект имеет обязательное свойство `defined_by` — строковый `id` (UUIDv7) объекта **системного слоя**, который его определяет (DL-013).
- Значение зависит от слоя объекта:

| `layer` объекта | На что указывает `defined_by` |
|---|---|
| `content` | на определение типа (`type: type`) с `type_value`, равным `type` объекта |
| `classification` | на встроенный метатип `domain`, `hierarchical-category`, `facet` или `facet-value` |
| `system` | на встроенный метатип из [`03-builtin-types.md`](03-builtin-types.md) |

- Объект, на который указывает `defined_by`, обязан существовать, иметь `layer: system` и `type: type`.
- Согласованность обязательна: `type_value` объекта-определения равен `type` объекта (INV-13); при расхождении оба объекта невалидны.
- Точка замыкания: у встроенного метатипа `type` значение `defined_by` равно его собственному `id` (единственная допустимая самоотсылка).
- `defined_by` указывает на **прямое** определение типа объекта, а не на его предка по цепочке `extends`: у экземпляра типа-потомка это `id` определения потомка (INV-18, [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md), I5).
- Свойство неизменяемо в том же смысле, что и `type`: смена `defined_by` у объекта в `accepted` не рекомендуется и равносильна смене типа.
- `defined_by` хранит «сырой» UUID строкой и является единственным исключением из канонической формы ссылки (INV-15): значение предназначено для машинной проверки согласованности, а не для навигации.

## Как контролируются инварианты

- Фаза 1 фиксирует семантику; машиночитаемый контроль (JSON Schema, правила валидации как объекты) — фаза 2 (`schema/`, `docs/validation/`), начата в iter-009: три схемы JSON Schema 2020-12 и восемь правил первой волны ([`../adr/ADR-009-phase2-schemas.md`](../adr/ADR-009-phase2-schemas.md), DL-036…DL-039).
- До появления валидации действует правило: объект, нарушающий любой инвариант, не считается принятым и не используется как источник определений.
- Перенос инвариантов в правила валидации должен сохранять их ID (INV-NN), чтобы документация и схема ссылались на одни и те же пункты; обе части реестра ([`09-structural-invariants.md`](09-structural-invariants.md)) используют единую нумерацию.
- Кандидаты в правила валидации фазы 2 в первую очередь: INV-02 (уникальность `id`), INV-06 (соответствие имени файла свойствам), INV-08 (`aliases[0] = title`), INV-09 (соответствие `layer` и `type`), INV-12–INV-13 (согласованность `defined_by` и `type_value`, уникальность `type_value`), INV-15 (форма ссылок), INV-16–INV-17 (уникальность ключей свойств и отношений), INV-18 (ацикличность `extends`, родитель — не метатип, глубина ≤ 5), INV-19 (существование ключей в `excludes`, запрет универсальных свойств), INV-20 (`field_order` ⊆ набора цепочки), INV-21 (`value_type` из набора, наличие `enum_values`), INV-23 (цель `media` — объект `type: image`), INV-24 (наличие `attachment` у `image`), INV-25 (состав ключей правила развёртывания, существование определений в `trigger_property`, `adds_properties`, `adds_relations`, `trigger_values` ⊆ `enum_values`), INV-26 (детерминированный пересчёт эффективного набора полей при изменении значения триггера), INV-27 (предупреждение об осиротевших значениях неактивных полей, запрет автоматического удаления).
- Реализовано в первой волне (iter-009): схемами — форма восьми обязательных свойств, форма `id` (INV-01), непустые `title` и `aliases`, наборы `layer` и `status`, соответствие `layer` и `type` (INV-09), форма и состав определений системного слоя (INV-13, INV-15…INV-17, INV-19, INV-21, INV-22, INV-25), обёртка `image` и значения `media` / `list<media>` (INV-23, INV-24); правилами — уникальность `id` (INV-02), соответствие имени файла (INV-05, INV-06), `aliases[0] = title` (INV-08), тип цели `media` (INV-23), наличие `attachment` (INV-24), ацикличность `extends` (INV-18), согласованность `defined_by` и `type_value` (INV-12, INV-13), `trigger_values` ⊆ `enum_values` (INV-25). Остальные кандидаты — вторая волна ([`../validation/00-validation-rules.md`](../validation/00-validation-rules.md), раздел 7).
