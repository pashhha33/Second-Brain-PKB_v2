# Инварианты объекта

Жёсткие правила, которым обязан удовлетворять любой объект Second Brain PKB — экземпляр, элемент классификации и определение типа. Инвариант нарушен ⇒ объект невалиден; контроль выполняется правилами валидации (фаза 2), здесь зафиксирована только семантика.

Формулировки инвариантов нормативны. Обоснования выбора формата `id`, правила имени файла и производности `type_prefix` — в [`../adr/ADR-001-identity-and-typing.md`](../adr/ADR-001-identity-and-typing.md); обоснование трёхслойной модели и связи объекта с определением — в [`../adr/ADR-002-three-layers.md`](../adr/ADR-002-three-layers.md); обоснование пары key/label и канонической формы ссылки — в [`../adr/ADR-003-properties-links.md`](../adr/ADR-003-properties-links.md); обоснование наследования типов — в [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md); источники решений — [`../decisions/decision-log.md`](../decisions/decision-log.md) (DL-003, DL-006…DL-021).

Нумерация стабильна: в редакции iter-001 пункт INV-12 описывал самоописание схемы в целом; с iter-002 он разделён на INV-12 (`defined_by` — связь объекта с определением), INV-13 (`type_value`) и INV-14 (встроенные метатипы). В iter-003 добавлены INV-15 (каноническая форма ссылки), INV-16 (`property_key`) и INV-17 (`relation_key`). В iter-004 добавлены INV-18…INV-20 (наследование типов), INV-21 (`value_type`) и INV-22 (`label` определений системного слоя). Номера INV-01…INV-14 сохраняют значение, правила фазы 2 обязаны использовать текущие номера.

## Обязательные свойства объекта

Минимальный набор свойств любого объекта (детали — в INV-01…INV-12):

```yaml
id: 01a17d3b-5d88-74e5-a071-8293a4b5c6d7              # UUIDv7, string
type: person                                            # string, ASCII kebab-case
defined_by: 01a17d3b-4de8-70a1-ac3d-4e5f60718293       # id определения типа (system)
title: Иван Петров                                      # string, непустой
aliases:
  - Иван Петров                                         # aliases[0] === title
layer: content                                          # system | classification | content
status: accepted                                        # draft | accepted | deprecated
owner: human                                            # string, непустой
```

Имя файла этого объекта: `person_01a17d3b-5d88-74e5-a071-8293a4b5c6d7.md`.

## Универсальные инварианты

### INV-01 — формат `id`

- Каждый объект имеет свойство `id` типа string.
- Значение — **UUIDv7** (RFC 9562): версия `7`, вариант RFC (`8`, `9`, `a` или `b`).
- Хранится в канонической форме: 36 символов, строчные шестнадцатеричные цифры, дефисы на позициях 9, 14, 19, 24 (индексация с 1). Пример: `01a17d3b-5d88-74e5-a071-8293a4b5c6d7`.
- Другие форматы `id` (ULID, UUIDv4, числовые счётчики, «человеческие» slug-идентификаторы) не допускаются — один формат на всю модель.
- Следствие: лексикографическая сортировка канонических строк `id` совпадает с хронологией их выдачи.

### INV-02 — уникальность `id`

- Область уникальности — **всё хранилище (vault)**, включая объекты системного слоя. Пространство `id` единое, разделения по слоям нет.
- Два объекта с одинаковым `id` — ошибка данных, а не слияние.
- Уникальность контролируется правилами валидации фазы 2; до их появления — проверкой при создании объекта.

### INV-03 — неизменяемость `id`

- `id` выдаётся один раз — при создании объекта — и **никогда не меняется**: ни при переименовании файла, ни при смене `title`, ни при изменении `type`, ни при переносе объекта в другую папку.
- Фиксированные `id` встроенных метатипов ([`03-builtin-types.md`](03-builtin-types.md)) неизменяемы в той же мере: их замена равносильна замене модели.
- Объект, которому требуется другая идентичность, создаётся заново (новый `id`), а старый переводится в `status: deprecated` (INV-10).
- `id` — единственная стабильная основа ссылок, включая `defined_by` (INV-12); всё, что может меняться (`title`, имя файла, путь), стабильным не считается.

### INV-04 — `type`

- Каждый объект имеет свойство `type` типа string — тип сущности (DL-003, DL-007).
- Значение непустое, в **ASCII kebab-case**: `[a-z0-9]+(-[a-z0-9]+)*`, без пробелов, подчёркиваний и не-ASCII символов. Человекочитаемое имя типа хранится в `title` объекта-типа, а не в значении `type`.
- `type` согласован с `defined_by` (INV-12): объект, на который указывает `defined_by`, обязан быть определением типа с `type_value`, равным значению `type`.
- Множество допустимых значений `type` открыто: девять встроенных метатипов ([`03-builtin-types.md`](03-builtin-types.md)) плюс любые пользовательские типы, созданные как объекты системного слоя.
- После перехода объекта в `status: accepted` смена `type` **не рекомендуется**; при необходимости смены типа создаётся новый объект (см. «Последствия» в ADR-001).

### INV-05 — `type_prefix`

- `type_prefix` — короткий префикс имени файла, **производный** от значения `type` (DL-007): он не задаётся вручную независимо от `type` и не хранится как независимый источник истины.
- Правило вычисления (DL-009, статус Accepted; ADR-001, R3):
  1. привести `type` к нижнему регистру (по INV-04 уже в нижнем);
  2. заменить последовательности разделителей (пробел, `_`, `.`, `/`) одним дефисом;
  3. удалить все символы, кроме `[a-z0-9-]`;
  4. удалить дефисы в начале и в конце строки;
  5. если длина результата больше 16 символов — обрезать до 16 и удалить дефис в конце строки;
  6. если результат пуст — объект невалиден (тип обязан давать непустой префикс; не-ASCII имена типов запрещены INV-04).
- Примеры (для значений `type`, удовлетворяющих INV-04): `person` → `person`; `literature-note` → `literature-note` (15 символов, без обрезки); `hierarchical-category` → `hierarchical-cat` (обрезка до 16); `book-2` → `book-2`.
- Шаги 1–3 для корректного `type` тождественны и нужны как защита от ручных правок значения (например, `Literature Note` → `literature-note`).
- Коллизия префиксов у двух разных типов (например, после обрезки) фиксируется переименованием одного из типов до его перехода в `accepted`; механизма ручных переопределений префикса в фазе 1 нет.

### INV-06 — имя файла

- Имя файла заметки: **`{{type_prefix}}_{{id}}`** плюс расширение формата хранения (для Obsidian — `.md`). Разделитель префикса и `id` — одно подчёркивание.
- Пример: `person_01a17d3b-5d88-74e5-a071-8293a4b5c6d7.md`.
- Имя файла уникально в пределах хранилища как следствие INV-02 (уникальность `id`); путь (папка) частью идентичности не является и может меняться.
- Имя файла не содержит символов, запрещённых в именах файлов Obsidian и распространённых ОС: допустимы только `[a-z0-9-]` (префикс), `_` (разделитель), `[0-9a-f-]` (`id`) и `.` перед расширением.
- `id` в имени файла обязан совпадать со значением свойства `id`; `type_prefix` — с префиксом, вычисленным из `type`. Расхождение — признак ручной правки и ошибка данных (контроль — фаза 2).
- Переименование файла не меняет `id`. Переименование файла требуется только в одном случае: изменился `type` объекта (не рекомендуется после `accepted`).

### INV-07 — `title`

- Каждый объект имеет обязательное свойство `title` типа string — читаемое имя сущности (DL-008).
- Значение непустое после удаления пробелов по краям; может содержать любые символы, включая кириллицу и пробелы.
- `title` изменяем: смена `title` не меняет ни `id`, ни имя файла, ни `type_value` определения типа (INV-13).
- `title` — единственное свойство, которое показывается пользователю как имя объекта в списках, графе и результатах поиска.

### INV-08 — `aliases[0] = title`

- Свойство `aliases` — непустой список строк; его **первый элемент всегда равен значению `title`** (точное совпадение строки после удаления пробелов по краям).
- Инвариант действует постоянно: при создании объекта и при любом изменении `title` значение `aliases[0]` синхронизируется с ним.
- Назначение: ссылки вида `[[title]]` и поиск по имени работают без обращения к `id`; дублирование делает имя объекта видимым для механизмов Obsidian, работающих с `aliases`.
- Элементы `aliases[1..]` — произвольные дополнительные имена; ограничений на их состав в фазе 1 нет.

### INV-09 — `layer`

- Каждый объект имеет свойство `layer` с одним из трёх значений (DL-010, DL-012):
  - `system` — описывает, как устроена модель: встроенные метатипы, определения типов (включая пользовательские), определения свойств и отношений, правила валидации, автоматизации;
  - `classification` — описывает, как объекты группируются: домены, узлы иерархических категорий, фасеты и значения фасетов;
  - `content` — знания предметной области: экземпляры пользовательских типов.
- Значение `layer` согласовано со значением `type`:
  - `type` ∈ {`domain`, `hierarchical-category`, `facet`, `facet-value`} ⇒ `layer: classification`;
  - `type` ∈ {`type`, `property`, `relation`, `automation`, `validation-rule`} ⇒ `layer: system`;
  - прочие значения `type` ⇒ `layer: content`.
- Расхождение `layer` и `type` — ошибка данных (правило валидации фазы 2).
- Слой не выводится из имени файла и не кодируется в пути: `layer` — явное свойство (ADR-002, А1).
- Подробно — [`02-layers.md`](02-layers.md).

### INV-10 — `status`

- Каждый объект имеет свойство `status` с одним из значений: `draft`, `accepted`, `deprecated` (DL-011).
- Семантика:
  - `draft` — объект может меняться свободно; экземпляры типа в `draft` считаются черновыми и не используются как основа автоматизаций;
  - `accepted` — объект стабилен; действуют ограничения на смену `type` (INV-04) и на изменение определений системного слоя;
  - `deprecated` — объект выведен из эксплуатации: он сохранён, ссылки на него действительны, новые объекты по нему не создаются.
- Ограничения: встроенные метатипы не переводятся в `deprecated` (INV-14); перевод определения типа в `deprecated` требует решения о судьбе его экземпляров; `deprecated` не означает удаление файла.
- Расширение набора значений — через DL и обновление этого файла.

### INV-11 — `owner`

- Каждый объект имеет свойство `owner` типа string — ответственного за объект (человек или процесс).
- Значение непустое. В персональной базе знаний по умолчанию `human`.
- `owner` не участвует в формировании имени файла и не является ссылкой на объект в фазе 1.

### INV-12 — `defined_by`: связь объекта с определением

- Каждый объект имеет обязательное свойство `defined_by` — строковый `id` (UUIDv7) объекта **системного слоя**, который его определяет (DL-013).
- Значение зависит от слоя объекта:

| `layer` объекта | На что указывает `defined_by` |
|---|---|
| `content` | на определение типа (`type: type`) с `type_value`, равным `type` объекта |
| `classification` | на встроенный метатип `domain`, `hierarchical-category`, `facet` или `facet-value` |
| `system` | на встроенный метатип из [`03-builtin-types.md`](03-builtin-types.md) |

- Объект, на который указывает `defined_by`, обязан существовать, иметь `layer: system` и `type: type`.
- Согласованность обязательна: `type_value` объекта-определения равен `type` объекта (INV-13); при расхождении оба объекта невалидны.
- Точка замыкания: у встроенного метатипа `type` значение `defined_by` равно его собственному `id` (единственная допустимая самоотсылка).
- `defined_by` указывает на **прямое** определение типа объекта, а не на его предка по цепочке `extends`: у экземпляра типа-потомка это `id` определения потомка (INV-18, [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md), I5).
- Свойство неизменяемо в том же смысле, что и `type`: смена `defined_by` у объекта в `accepted` не рекомендуется и равносильна смене типа.
- `defined_by` хранит «сырой» UUID строкой и является единственным исключением из канонической формы ссылки (INV-15): значение предназначено для машинной проверки согласованности, а не для навигации.

## Структурные инварианты системного слоя

### INV-13 — `type_value` у определений типов

- Объект с `type: type` (определение типа) обязан иметь свойство `type_value` — строку в ASCII kebab-case (INV-04), которую используют в свойстве `type` его экземпляры.
- `type_value` уникален в пределах хранилища: два определения типа с одинаковым `type_value` не допускаются.
- `type_value` неизменяем после перехода определения в `status: accepted`: его изменение меняет тип всех экземпляров и требует перевода определения в `deprecated` и создания нового.
- `type_value` **не наследуется**: у определения типа с `extends` собственное уникальное значение; совпадение `type_value` потомка и предка запрещено (INV-18). Принадлежность предку (`is_a`) в данных не хранится и вычисляется по цепочке `extends`.
- Свойство `title` определения типа может отличаться от `type_value` (например, `title: Иерархическая категория` при `type_value: hierarchical-category`) и изменяемо (INV-07); для определений, создаваемых пользователем и ядром, `title` задаётся на русском и одновременно служит `label` (INV-22).

### INV-14 — встроенные метатипы

- Девять встроенных метатипов ([`03-builtin-types.md`](03-builtin-types.md)) присутствуют в хранилище с момента инициализации и имеют фиксированные `id`, `type`, `type_prefix`, `title` и `aliases` (`aliases[1]` — русское имя).
- Их `status` всегда `accepted`; `layer` всегда `system`; `owner` — `human`.
- Встроенные метатипы не удаляются, не переименовываются и не переводятся в `deprecated`: это ломает самоописание модели и обесценивает `defined_by` существующих объектов.
- Новый встроенный метатип добавляется только через DL с обновлением реестра.

### INV-15 — каноническая форма внутренней ссылки

- Внутренняя ссылка на объект имеет форму `[[{{type_prefix}}_{{id}}|{{title}}]]` (DL-015):
  - часть до `|` — имя файла объекта-цели без пути и расширения (INV-06);
  - часть после `|` — значение `title` объекта-цели (INV-07).
- Ссылки вида `[[имя_файла]]` (без alias), `[[title]]` и `[[путь/имя_файла]]` каноническими не являются; плагин нормализует их к канонической форме.
- При изменении `title` цели alias во всех ссылках на неё обновляется; цель ссылки не меняется, так как `id` неизменяем (INV-03).
- Значения отношений хранятся в frontmatter объекта-источника под ключом `relation_key` именно в канонической форме (INV-17, [`04-properties-relations.md`](04-properties-relations.md), разделы 4–5).
- Единственное исключение — `defined_by` (INV-12): хранит UUID строкой.
- Подробно и с альтернативами — [`../adr/ADR-003-properties-links.md`](../adr/ADR-003-properties-links.md).

### INV-16 — `property_key` и `label` у определений свойств

- Объект с `type: property` обязан иметь свойство `property_key` — машинный идентификатор свойства (DL-014): строка в ASCII (`[a-z0-9_]+(-[a-z0-9_]+)*`), уникальная в пределах хранилища, неизменяемая после `accepted`.
- Значение свойства в заметке хранится в frontmatter под ключом, равным `property_key`.
- `label` свойства равен `title` объекта-свойства (INV-07): отдельное поле `label` не вводится.
- `aliases[1]` объекта-свойства равен `property_key` (поиск и по русскому имени, и по машинному ключу).
- Правило `label` = `title` распространяется на все определения системного слоя (INV-22).
- Встроенные свойства и их определения — в [`04-properties-relations.md`](04-properties-relations.md), раздел 2.

### INV-17 — `relation_key` у определений отношений

- Объект с `type: relation` обязан иметь свойство `relation_key` — машинный идентификатор отношения (DL-014): строка в ASCII, уникальная в пределах хранилища, неизменяемая после `accepted`.
- Определение отношения также обязано иметь `source_type`, `target_type` (списки значений `type_value`) и `cardinality` (`0..1`, `1..1`, `0..*`, `1..*`); `inverse_key` — только если обратная связь хранится явно.
- Значение отношения хранится в объекте-источнике под ключом `relation_key` в канонической форме ссылки (INV-15).
- Встроенные отношения классификации — в [`04-properties-relations.md`](04-properties-relations.md), раздел 5.

### INV-18 — `extends`: одиночное линейное наследование

- Определение типа (`type: type`) может иметь ключ `extends` кратности `0..1` — каноническую внутреннюю ссылку (INV-15) на другое определение типа (DL-017).
- Родителем может быть только определение типа, **не являющееся встроенным метатипом** (INV-14): наследование метатипа смешало бы слои (INV-09). Встроенные метатипы `extends` не имеют.
- Наследование определено для определений типов, чьи экземпляры относятся к слою `content`.
- Цепочка `extends` линейна (не более одного родителя) и **ациклична**: тип не может быть собственным предком. Защита — при сохранении определения и правилом валидации фазы 2.
- Рекомендуемая глубина цепочки — до 5 уровней; превышение является предупреждением, а не ошибкой.
- `extends` у определения в `status: accepted` не меняется: смена родителя меняет эффективный набор полей (INV-20) всех экземпляров. Замена — новое определение типа и `deprecated` старого (по образцу INV-13).
- Подробно, с альтернативами и жизненным циклом, — [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md) (I1, I6).

### INV-19 — `excludes`: исключение унаследованных полей

- Ключ `excludes` определения типа — список значений `property_key` и `relation_key`, кратность `0..*` (DL-017).
- Каждый элемент обязан указывать на существующее определение свойства или отношения и фактически входить в наследуемый набор цепочки; «пустое исключение» — предупреждение правила валидации фазы 2.
- Универсальные обязательные свойства (`id`, `type`, `defined_by`, `title`, `aliases`, `layer`, `status`, `owner`) и `type_value` через `excludes` не отменяются: их наличие задано INV-01…INV-13, а не наследованием. Такой ключ в `excludes` — ошибка данных.
- Исключение, объявленное в типе X, действует на X и на всех его потомков; потомок отменяет его явным перечислением ключа в своём `field_order` (INV-20, nearest wins).

### INV-20 — эффективный набор полей и порядок представления

- **Эффективный набор полей** типа — множество ключей свойств и отношений, применимых к его экземплярам: ключ входит в набор, если у определения `applies_to` = `*` либо `applies_to` содержит этот тип или любого его предка по цепочке `extends`, и ключ не исключён по INV-19.
- **Nearest wins:** ключ, объявленный на нескольких уровнях цепочки, входит в набор один раз и принадлежит ближайшему к листу уровню.
- **Порядок представления** детерминирован и одинаков для форм плагина и для JSON Schema фазы 2: (1) универсальные обязательные свойства в порядке номеров реестра; (2) унаследованные поля от корня к листу, внутри уровня — по возрастанию `id` определения; (3) собственные поля в порядке `field_order`, затем неперечисленные в нём — по возрастанию `id` определения.
- `field_order` — список ключей собственных полей типа; допускаются только ключи, входящие в набор цепочки до применения `excludes`. Перечисление несуществующего ключа — ошибка данных.
- Параметры поля (`value_type`, `required`, `cardinality`, `enum_values`, `label`) на уровне типа **не переопределяются**: они остаются атрибутами определения свойства или отношения (INV-16, INV-17, INV-21). Ужесточение требования у потомка выражается отдельным свойством потомка или правилом валидации.

### INV-21 — `value_type` из канонического набора

- `value_type` определения свойства или отношения принимает одно из 12 канонических значений: `string`, `text`, `number`, `boolean`, `date`, `datetime`, `enum`, `list<string>`, `list<enum>`, `link`, `list<link>`, `uuid` ([`04-properties-relations.md`](04-properties-relations.md), раздел 1.1; DL-018).
- Набор закрыт: новое значение добавляется только через DL с обновлением реестра. Значения `object` / `json` в набор не входят.
- `enum` и `list<enum>` требуют непустого `enum_values` в определении; `link` и `list<link>` хранятся в канонической форме (INV-15); `uuid` — «сырой» UUIDv7 (INV-01).
- `value_type` определения в `status: accepted` неизменяем; замена выполняется новым определением и переводом старого в `deprecated`.

### INV-22 — `label` определений системного слоя

- Для любого определения системного слоя (`type: type`, `property`, `relation`, `validation-rule`, `automation`) **`label` = `title`** (INV-07); отдельное поле `label` не вводится (DL-021).
- `key` определения — `type_value`, `property_key` или `relation_key` — в интерфейсе выступает индикатором (подпись, бейдж, tooltip), а не именем объекта.
- `title` (= `label`) определений, создаваемых пользователем и ядром, задаётся на русском; `key` — английский ASCII (INV-04, INV-16, INV-17); `aliases[1]` определения хранит его `key`.
- Исключение — девять встроенных метатипов: их `title` зафиксирован реестром на английском, русское имя — в `aliases[1]` (INV-14).
- Подробно — [`../adr/ADR-004-type-inheritance.md`](../adr/ADR-004-type-inheritance.md) (I7) и [`04-properties-relations.md`](04-properties-relations.md), раздел 1.2.

## Как контролируются инварианты

- Фаза 1 фиксирует семантику; машиночитаемый контроль (JSON Schema, правила валидации как объекты) — фаза 2 (`schema/`, `docs/validation/`).
- До появления валидации действует правило: объект, нарушающий любой инвариант, не считается принятым и не используется как источник определений.
- Перенос инвариантов в правила валидации должен сохранять их ID (INV-NN), чтобы документация и схема ссылались на одни и те же пункты.
- Кандидаты в правила валидации фазы 2 в первую очередь: INV-02 (уникальность `id`), INV-06 (соответствие имени файла свойствам), INV-08 (`aliases[0] = title`), INV-09 (соответствие `layer` и `type`), INV-12–INV-13 (согласованность `defined_by` и `type_value`, уникальность `type_value`), INV-15 (форма ссылок), INV-16–INV-17 (уникальность ключей свойств и отношений), INV-18 (ацикличность `extends`, родитель — не метатип, глубина ≤ 5), INV-19 (существование ключей в `excludes`, запрет универсальных свойств), INV-20 (`field_order` ⊆ набора цепочки), INV-21 (`value_type` из набора, наличие `enum_values`).
