# ADR-001: Идентичность и типизация объекта

Архитектурное решение о том, как объект получает идентификатор, как формируется имя файла заметки, какова семантика `type` и `type_prefix`, и какие свойства имени (`title`, `aliases`) обязательны.

## Контекст

Second Brain PKB — самоопределяющаяся модель: тип, свойство и отношение являются объектами того же хранилища, что и экземпляры. Отсюда следуют требования, которые нельзя отложить до фазы реализации плагина:

1. **Идентичность без внешнего реестра.** У объекта должен быть идентификатор, который не зависит ни от пути в хранилище, ни от имени, ни от типа, ни от кода плагина. Иначе перенос файла или переименование сущности ломает ссылки.
2. **Имя файла как единственный «человеческий» якорь.** В Obsidian заметка адресуется именем файла; оно видно в проводнике, в ссылках и в поиске. Имя должно быть уникальным, предсказуемым и формируемым по одному правилу для всех объектов — и для определений схемы, и для экземпляров.
3. **Один формат идентификатора на всю модель.** Смешение форматов (числовые счётчики, slug-имена, разные версии UUID) делает невозможной универсальную валидацию и усложняет плагин.
4. **Читаемость против стабильности.** Пользователь хочет видеть в базе «Иван Петров», а не `019a1b2c-…`. Нужен механизм, который даёт читаемое имя, не превращая его в идентификатор.
5. **Расширяемость без правки кода.** Новый тип = новая заметка. Значит, правило имени файла не может содержать перечня типов, зашитого в плагине.

Ограничения: офлайн-работа, отсутствие сервера выдачи идентификаторов, файловая система как носитель (ограничения на длину и состав символов имени файла), стек плагина — TypeScript + Obsidian API (DL-005).

Человеком зафиксированы обязательные пункты: формат `id` — UUIDv7; имя файла — `{{type_prefix}}_{{id}}`; `type_prefix` — короткий префикс, производный от `type`; `type` хранит тип сущности; `title` — читаемое имя; значение `title` обязательно дублируется в `aliases[0]`. Настоящий ADR фиксирует эти решения и уточняет производные правила (вычисление `type_prefix`, область уникальности, неизменяемость).

## Решение

### R1. `id` — UUIDv7

- Каждый объект имеет свойство `id` типа string в формате **UUIDv7** (RFC 9562).
- Хранение — каноническая строчная форма, 36 символов: `xxxxxxxx-xxxx-7xxx-yxxx-xxxxxxxxxxxx`, где `y` ∈ {`8`, `9`, `a`, `b`}.
- Формат единственный для всей модели: все слои и все типы объектов.
- `id` генерируется локально в момент создания объекта; сервер и координация не требуются.

### R2. Имя файла — `{{type_prefix}}_{{id}}`

- Имя файла заметки: `{{type_prefix}}_{{id}}` + расширение формата хранения (`.md` для Obsidian).
- Пример: `person_019a1b2c-7d3e-7f40-8a1b-2c3d4e5f6a70.md`.
- Разделитель — одно подчёркивание; регистр — строчный; `id` — в той же канонической форме, что и в свойстве `id`.
- Имя файла уникально в пределах хранилища; путь (папка) частью идентичности не является.

### R3. `type_prefix` производен от `type`

`type_prefix` не является независимым свойством: он **вычисляется** из значения `type`. Правило фиксируется DL-009 (подтверждён, статус Accepted — см. примечание в разделе «Статус»):

1. привести значение к нижнему регистру;
2. заменить каждую последовательность разделителей (пробел, `_`, `.`, `/`) одним дефисом;
3. удалить все символы, кроме `[a-z0-9-]`;
4. удалить дефисы в начале и в конце строки;
5. обрезать до 16 символов, затем удалить дефис в конце (если он появился после обрезки);
6. если результат пуст — объект невалиден.

Допустимый алфавит результата: `[a-z0-9-]`. Свойство `type` обязано быть в ASCII kebab-case (`[a-z0-9]+(-[a-z0-9]+)*`), поэтому шаги 1–4 для корректного `type` являются тождественными и служат защитой от ручных правок.

Примеры:

| `type` | `type_prefix` | имя файла (фрагмент) |
|---|---|---|
| `person` | `person` | `person_019a1b2c-….md` |
| `type` | `type` | `type_019a1b2c-….md` |
| `validation-rule` | `validation-rule` | `validation-rule_019a1b2c-….md` |
| `automation-trigger` | `automation-trigg` | `automation-trigg_019a1b2c-….md` |
| `reading-note-highlights` | `reading-note-hig` | `reading-note-hig_019a1b2c-….md` |

### R4. Семантика `type`

- `type` — обязательное строковое свойство, хранящее тип сущности (DL-003, DL-007).
- Значение `type` у экземпляра — идентификатор типа, определённый объектом системного слоя; у объекта системного слоя — один из встроенных метатипов.
- `type` — не отображаемое имя и не свободный текст: человекочитаемое имя хранится в `title` объекта-типа.
- `type` определяет ожидаемый набор свойств и отношений экземпляра (детализация — в следующих итерациях фазы 1).

### R5. `title` обязателен, `aliases[0] = title`

- Каждый объект имеет обязательное свойство `title` — непустую строку, читаемое имя сущности.
- Свойство `aliases` — непустой список строк; **`aliases[0]` всегда равен `title`** (точное совпадение после удаления пробелов по краям). Инвариант поддерживается при создании и при каждом изменении `title`.
- `title` изменяем; его изменение не меняет ни `id`, ни имя файла.
- Элементы `aliases[1..]` — дополнительные имена без ограничений в фазе 1.

### R6. Область уникальности

- Уникальность `id` — в пределах **всего хранилища (vault)**, включая объекты системного слоя. Пространство идентификаторов единое.
- Уникальность имени файла — следствие уникальности `id` и детерминированности `type_prefix`.
- Уникальность `title` **не требуется**: два объекта могут иметь одинаковое читаемое имя; различаются они по `id` и имени файла.

### R7. Неизменяемость `id` и ограничение на смену `type`

- `id` выдаётся один раз и не меняется никогда: ни при переименовании файла, ни при смене `title`, ни при смене `type`, ни при переносе между папками.
- Объект, которому нужна другая идентичность, создаётся заново; старый перестаёт быть `accepted`.
- **Рекомендация (не жёсткий запрет):** после перехода объекта в `status: accepted` значение `type` не меняется. Смена типа у принятого объекта — это смена имени файла и семантики всех его свойств; при необходимости создаётся новый объект, а старый выводится из `accepted`.
- Смена `type` у объекта в `status: draft` допустима и влечёт переименование файла по R2.

## Альтернативы

### А1. Формат идентификатора

| Вариант | Суть | Оценка |
|---|---|---|
| **UUIDv7 (принято)** | 128 бит, RFC 9562, первые 48 бит — время Unix в мс | Сортируемость по времени создания, стандарт, генерация офлайн, коллизии практически исключены, поддержка в современных рантаймах. Минус: 36 символов, нечитаем для человека |
| ULID | 128 бит, Crockford Base32, 26 символов | Короче и тоже сортируем по времени. Отклонён: нестандартный для экосистемы формат, требует соглашения о регистре и алфавите, отсутствует в RFC, хуже поддержка инструментами; решение человека — UUIDv7 |
| UUIDv4 | 128 бит, полностью случайный | Отклонён: нет сортируемости по времени, нельзя восстановить порядок создания объектов, что полезно для диагностики и для «недавних объектов» |
| slug + счётчик (`person-0007`) | Короткий, читаемый | Отклонён: требует централизованного реестра и контроля уникальности при слиянии хранилищ; читается как имя, поэтому провоцирует переименования; нарушает принцип «идентичность не зависит от имени» |
| Хеш от пути/содержимого | Идентификатор производен от файла | Отклонён: меняется при переименовании и правке, то есть не является идентификатором |

### А2. Правило вычисления `type_prefix`

| Вариант | Суть | Оценка |
|---|---|---|
| **Полный slug `type` с ограничением 16 символов (принято)** | kebab-case, детерминированно, без ручного ввода | Префикс самодокументируем, вычисляется однозначно, не требует реестра. Риск: обрезка длинных имён и теоретическая коллизия после обрезки — см. «Последствия» |
| Первая лексема (`reading-note-highlights` → `reading`) | Короткий | Отклонён: коллизии для типов, начинающихся одинаково (`reading-note`, `reading-session`), потеря различимости |
| Аббревиатура (`reading-note` → `rn`) | Минимальная длина | Отклонён: нечитаем, неоднозначен, требует ручного назначения, то есть перестаёт быть производным от `type` |
| Ручной реестр соответствий `type` → `type_prefix` | Явный контроль | Отклонён в фазе 1: противоречит расширению модели без правки реестра и решению человека о производности префикса; может быть рассмотрен позже как механизм переопределения (см. «Последствия») |
| Хеш от `type` (4 символа) | Гарантированная длина | Отклонён: полностью нечитаем, коллизии требуют контроля, префикс перестаёт объяснять содержимое файла |

### А3. Правило именования файлов

| Вариант | Суть | Оценка |
|---|---|---|
| **`{{type_prefix}}_{{id}}` (принято)** | Тип + идентичность | Уникально, предсказуемо, тип виден в проводнике, не зависит от `title`. Решение человека |
| `{{title}}` | Только читаемое имя | Отклонён: не уникален, меняется, требует переименований и исправления ссылок, не несёт типа |
| `{{id}}` | Только UUID | Отклонён: уникально и стабильно, но проводник хранилища становится нечитаемым; тип не виден без открытия заметки |
| `{{title}}_{{id}}` | Читаемость + уникальность | Отклонён: имя файла становится зависимым от изменяемого `title`; длина имени растёт; требует нормализации `title` под ограничения ФС |
| `{{type}}/{{id}}` (тип как папка) | Тип в пути | Отклонён: путь перестаёт быть стабильным, перенос между папками ломает адресацию, слои модели оказываются в разных деревьях |
| `{{type_prefix}}-{{id}}` (дефис вместо подчёркивания) | Иной разделитель | Отклонён: дефис уже используется внутри `type_prefix` и внутри UUID, поэтому граница между префиксом и `id` становится неоднозначной при разборе имени |

## Последствия

**Положительные:**

- Идентичность полностью отделена от имени, пути и типа: переименование и перенос заметок безопасны.
- Правило имени файла универсально и не содержит перечня типов — новый тип не требует правки кода плагина.
- UUIDv7 даёт хронологический порядок создания объектов без дополнительных свойств и без сервера.
- Единое пространство `id` исключает коллизии между слоем схемы и слоем экземпляров.
- `aliases[0] = title` обеспечивает работу ссылок и поиска по читаемому имени при сохранении стабильного `id`.
- Инварианты переносятся в JSON Schema и правила валидации фазы 2 без изменения семантики.

**Отрицательные и риски:**

- Имена файлов длинные (до 16 + 1 + 36 + 3 = 56 символов) и не читаются целиком как осмысленный текст. Компенсация: пользователь видит `title`, а не имя файла; префикс несёт тип.
- Имя файла не объясняет содержимое без `title`. Компенсация: `aliases[0] = title` и отображение `title` в интерфейсе.
- Обрезка `type_prefix` до 16 символов может дать коллизию двух разных типов (`reading-note-highlights` и `reading-note-highlighter` → `reading-note-hig`). Компенсация: имена файлов всё равно уникальны за счёт `id`; коллизия префикса мешает только визуальному различению типов. Правило: не принимать в `accepted` два типа с одинаковым префиксом; при необходимости — переименовать один из типов. Механизм ручного переопределения префикса отложен до появления реальной коллизии.
- Ограничение `type` на ASCII kebab-case запрещает имена типов на русском. Компенсация: русское имя типа хранится в `title` объекта-типа (согласуется с DL-001: идентификаторы — на английском).
- Дублирование `title` в `aliases[0]` создаёт риск рассинхронизации при ручной правке заметки. Компенсация: правило валидации фазы 2 и автоматизация синхронизации в плагине.
- Отказ от смены `id` делает невозможным «объединение» двух объектов в один с сохранением обеих идентичностей. Компенсация: один объект остаётся `accepted`, второй выводится из него со ссылкой на первый (процедура будет определена в следующей итерации фазы 1).

**Что фиксируется дополнительно:**

- DL-006 — `id` = UUIDv7, имя файла = `{{type_prefix}}_{{id}}`.
- DL-007 — семантика `type` и производность `type_prefix`.
- DL-008 — обязательность `title` и правило `aliases[0] = title`.
