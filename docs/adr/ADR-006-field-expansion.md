# ADR-006: Триггерные свойства и развёртывание полей (field expansion)

Архитектурное решение о механизме, при котором значение свойства-триггера определяет набор дополнительных полей объекта: правила развёртывания вводятся как объекты системного слоя `type: field-expansion` (новый встроенный метатип), семантика мультивыбора — объединение множеств (`mode: union`), смена значения триггера не удаляет данные.

## Контекст

1. **Состав полей типа не зависит от данных экземпляра.** До iter-006 эффективный набор полей определялся только типом и его цепочкой `extends` (INV-20): все экземпляры типа получали одинаковую форму. На практике состав полей зависит от значения другого поля: у аудиокниги есть длительность и чтец, у печатной книги — число страниц, у ИИ-изображения — модель, запрос и сид, у персоны-разработчика — специализация.
2. **Выражать это потомками типов нельзя.** Типы `audiobook`, `ebook`, `paper-book` дублировали бы `applies_to` свойств и `source_type` отношений, ломали бы роли `book` (ADR-005, S3: роль определяется составом данных, а не типом) и требовали от владельца выбирать тип до заполнения полей. Цепочки наследования при этом остались бы одноуровневыми, но число типов ядра выросло бы втрое только по одному признаку.
3. **Вшивать правила в определение типа — значит закрыть их от владельца.** Модель построена на принципе саморасширяемости (PROJECT_BRIEF, принцип 2): добавление сущности не меняет код плагина. Правила, записанные служебным ключом в определении типа, нельзя отключить, перевести в `deprecated`, переиспользовать для нескольких типов и увидеть в графе.
4. **Существующих метатипов недостаточно.** `validation-rule` проверяет данные и сообщает об ошибке, но не меняет состав полей; `automation` описывает действие по триггеру, но его семантика — изменение данных, а не представление полей. Использование любого из них смешало бы три разных механизма в одном реестре.
5. **Три канонических сценария заданы человеком**: `person` + `occupation` (мультивыбор, объединение наборов полей профессий), `book` + `format` (`ebook` / `paper` / `audiobook`), `image` + `creation-method` (при `ai-generated` — метаданные генерации). Механизм обязан покрывать и одиночный выбор, и мультивыбор.

Ограничения, которые нельзя нарушать: `id` неизменяем (INV-03); состав встроенных метатипов фиксирован и пополняется только через DL (INV-14); `label` = `title` у определений системного слоя (INV-22); `value_type` из закрытого набора 14 значений, `object` и `json` не вводятся (INV-21, DL-018, ADR-004 I3); ключи свойств и отношений уникальны (INV-16, INV-17); параметры поля не переопределяются на уровне типа (ADR-004, I3); значения не удаляются автоматически (принцип сохранности данных владельца).

## Решение

### S1. Правило развёртывания — объект системного слоя

- Введён встроенный метатип 10 — `field-expansion` (Field expansion, «Правило развёртывания полей»), `id` `01a17d3b-4a32-716d-82a6-503fe47a47a1`, смещение 50 единой последовательности генерации ([`../metamodel/03-builtin-types.md`](../metamodel/03-builtin-types.md); DL-029).
- Правило — объект `type: field-expansion`, `layer: system`, `status` и `owner` как у любого определения. Служебные ключи: `applies_to_type`, `trigger_property`, `trigger_values`, `adds_properties`, `adds_relations`, `mode` (таблица — [`../metamodel/04-properties.md`](../metamodel/04-properties.md), раздел 5).
- Состав правила нормативен: INV-25 фиксирует обязательность ключей, существование определений по ключам, `trigger_values` ⊆ `enum_values`, непустоту хотя бы одного из `adds_properties` / `adds_relations`.
- `id` правил не фиксируется реестром и выдаётся при создании (DL-019 по аналогии с типами ядра): правила настраиваются владельцем, канонические примеры — образец, а не реестр.
- Ключи в правиле — машинные идентификаторы (`property_key`, `relation_key`, `type_value`), а не ссылки и не `id`: они уникальны и неизменяемы после `accepted`, поэтому правило не требует пересчёта при переименовании `label`.

### S2. Триггер — свойство с закрытым набором значений

- Свойство-триггер имеет `value_type: enum` (одиночный выбор) или `list<enum>` (мультивыбор) и непустой `enum_values` ([`../metamodel/04-properties.md`](../metamodel/04-properties.md), раздел 2, правило 2). Сопоставление — точное совпадение строки.
- В реестр свойств ядра добавлены три триггера (записи 16–18): `occupation` (`list<enum>`, `person`), `format` (`enum`, `book`), `creation-method` (`enum`, `image`) со стартовыми `enum_values`; владелец вправе расширить набор в своём определении — данные при этом не ломаются (INV-21 неизменяем только `value_type`).
- Добавлены пять разворачиваемых свойств ядра (записи 19–23): `specialization` (`list<string>`), `model` (`string`), `prompt` (`text`), `seed` (`number`), `page-count` (`number`); свойство `duration` расширено по `applies_to` до `book`: аудиокнига хранит длительность тем же определением. Реестр ядра: 15 → 23 записи (DL-027).
- Ссылки на персон остаются отношениями, а не свойствами: для чтеца введено отношение ядра 14 — `narrator` (`source` → `person`, `0..*`, обратное «Озвученные работы»), поэтому правило развёртывания умеет добавлять и отношения (ключ `adds_relations`).

### S3. Семантика мультивыбора — `mode: union`

- Значение триггера может активировать несколько правил и несколько значений одного правила; результат — объединение множеств добавляемых полей. Объединение идемпотентно и коммутативно: порядок правил и дубликаты ключей на состав полей не влияют (INV-26, DL-028).
- Ключ `mode` обязателен и в v1 принимает единственное значение `union`; другие режимы (`first-match`, `override`) вводятся только через DL — зарезервированы, но не определены.
- Конфликтов значений не возникает: правило добавляет поле, а не значение; значение вводит владелец или автоматизация.

### S4. Эффективный набор полей экземпляра

- Эффективный набор полей экземпляра = эффективный набор полей его типа (INV-20) ∪ объединение `adds_properties` и `adds_relations` активных правил (INV-26). Правило активно, если оно в `accepted`, его `applies_to_type` покрывает тип объекта или его предка по `extends`, а значение триггера пересекается с `trigger_values`.
- Порядок представления детерминирован: поля типа, затем добавленные поля по возрастанию `id` правил и по порядку перечисления ключей; `field_order` типа переопределяет порядок (nearest wins).
- Развёртывание не меняет параметры определений (`value_type`, `required`, `cardinality`, `applies_to`) — ограничение ADR-004 (I3) сохраняется. Обязательность значения в активном поле выражается правилом валидации фазы 2.
- `excludes` определения типа приоритетнее развёртывания: исключённое поле не появляется, даже если его добавляет активное правило (INV-19).
- Алгоритм вычисления (6 шагов) нормативно зафиксирован в [`../metamodel/08-field-expansion.md`](../metamodel/08-field-expansion.md), раздел 4.

### S5. Смена и удаление значения триггера: данные не удаляются

- Принятая семантика: значения развёрнутых полей сохраняются в frontmatter, поле переходит в состояние **неактивного** — интерфейс скрывает его, валидатор фазы 2 выдаёт предупреждение «осиротевшее значение», а не ошибку (INV-27, DL-028).
- Автоматическое удаление запрещено; очистка неактивных полей — явная команда владельца с подтверждением. Возврат значения триггера делает поле снова активным: прежние значения видны без повторного ввода.
- Обоснование выбора — в А4: потеря данных необратима, а «вечно видимые» поля скрывают отсутствие основания.

### S6. Три канонических примера

Зафиксированы в [`../metamodel/08-field-expansion.md`](../metamodel/08-field-expansion.md), раздел 6, с YAML правил и таблицами добавляемых полей:

1. `person` + `occupation` — два правила (специализация; место работы через `adds_relations: [member-of]`), демонстрируют union при мультивыборе `[developer, teacher]`.
2. `book` + `format` — три правила: `paper` → `page-count`; `ebook` → `attachment`, `url`; `audiobook` → `duration` + `narrator`. Демонстрируют добавление существующих свойств ядра и отношения.
3. `image` + `creation-method` — одно правило: `ai-generated` → `model`, `prompt`, `seed`; для остальных значений правил нет. Обязательный `attachment` обёртки сохраняется (INV-24).

## Альтернативы

### А1. Где хранить правила развёртывания

| Вариант | Оценка |
|---|---|
| **Отдельные объекты системного слоя `type: field-expansion` (принято)** | Требование человека (вариант B); правило можно создать, отключить, перевести в `deprecated`, переиспользовать для нескольких типов, увидеть в графе; код плагина не меняется (принцип 2) |
| Служебный ключ в определении типа (`expansions: …`) | Отклонён: потребовал бы вложенных структур (`value_type: object` / `list<object>`), которые отклонены (DL-018, ADR-004 I3); правило нельзя отключить отдельно от типа; переиспользование между типами невозможно |
| Правила в коде плагина | Отклонён: противоречит принципу саморасширяемости; каждое новое правило требовало бы релиза |
| Правила в JSON Schema фазы 2 | Отклонён: схема описывает допустимые данные, а не состав полей экземпляра; к тому же фаза 2 ещё не начата, а механизм нужен сейчас |

### А2. Тип значения свойства-триггера

| Вариант | Оценка |
|---|---|
| **`enum` / `list<enum>` с `enum_values` (принято)** | Закрытый набор в определении свойства, сопоставление — точное совпадение строки, машиночитаемая проверка `trigger_values` ⊆ `enum_values`; владелец расширяет набор правкой определения без миграции данных |
| `link` / `list<link>` на объекты `facet-value` | Отклонён для v1: семантически верен для открытых наборов (профессии), но значения фасетов не имеют фиксированных `id` — правило привязывалось бы к объектам конкретного хранилища, а канонические примеры становились невоспроизводимыми. Расширение механизма на триггеры-ссылки — кандидат фазы 2+ |
| `string` / `list<string>` | Отклонён: сопоставление нестабильно (регистр, синонимы, опечатки), проверка `trigger_values` невозможна |

### А3. Какой метатип описывает правило

| Вариант | Оценка |
|---|---|
| **Новый встроенный метатип `field-expansion` (принято)** | Отдельный реестр и отдельные служебные ключи; `defined_by` однозначно отличает правило развёртывания от других системных объектов; состав встроенных метатипов пополняется через DL (INV-14, правило 4 реестра) |
| Расширить `validation-rule` ключом `action: expand` | Отклонён: смешивает проверку данных и представление полей; у правила валидации другие обязательные ключи (условие, сообщение), а `adds_properties` для него бессмысленны; отключение валидации не должно выключать поля формы |
| Использовать `automation` | Отклонён: семантика автоматизации — изменение данных по событию, а развёртывание данные не меняет; смешение привело бы к правилам, которые «срабатывают» при каждом пересчёте формы |
| Не вводить метатип, хранить правила как `property` со служебными ключами | Отклонён: `property_key` правила совпал бы с ключом поля frontmatter, а `value_type` и `applies_to` определения свойства неприменимы к правилу |

### А4. Поведение при смене или удалении значения триггера

| Вариант | Оценка |
|---|---|
| **Поле становится неактивным, данные сохраняются, предупреждение (принято)** | Обратимо: возврат значения триггера возвращает поле вместе с прежним значением; потеря данных исключена; владелец видит причину предупреждения и сам решает, чистить или нет |
| Автоматически удалять значения неактивных полей | Отклонён: случайная правка триггера необратимо уничтожает введённые данные (например, `prompt` и `seed` ИИ-изображения); противоречит принципу сохранности данных владельца |
| Оставлять поля видимыми как обычные | Отклонён: скрывает то, что значение больше не имеет основания, и размывает смысл механизма — состав формы перестал бы зависеть от триггера |

### А5. Режимы объединения

| Вариант | Оценка |
|---|---|
| **Только `union`, ключ `mode` обязателен (принято)** | Требование человека («мультивыбор → union»); ключ зарезервирован, поэтому добавление режима не меняет состав обязательных ключей правила |
| `union` + `first-match` сразу | Отклонён: `first-match` требует приоритетов и порядка правил, то есть нового механизма разрешения конфликтов, которого в v1 нет; «не раздувать первую версию» (TASK.md iter-006) |
| Без ключа `mode` | Отклонён: неявное поведение сложнее расширять; добавление ключа позже сломало бы существующие правила (новые обязательные ключи у принятого объекта) |

## Последствия

**Положительные:**

1. Состав полей формы зависит от данных без умножения типов: `book` остаётся одним типом при трёх форматах, `person` — одним типом при любом наборе профессий.
2. Правила — объекты: их можно добавлять, отключать и переводить в `deprecated` без изменения кода плагина (принцип 2), они видны в графе и связаны с определениями через ключи.
3. Механизм ортогонален наследованию: `extends` / `excludes` / `field_order` (ADR-004) работают как раньше, развёртывание лишь дополняет эффективный набор.
4. Данные владельца защищены: смена триггера ничего не удаляет (INV-27), а неактивные поля видны как предупреждение, а не как ошибка.
5. Фаза 2 получает готовый контракт: алгоритм вычисления детерминирован, поэтому правило валидации и JSON Schema строятся по одному описанию.

**Отрицательные и риски:**

1. Десятый встроенный метатип увеличивает объём bootstrap и число объектов системного слоя. Компенсация: правила не входят в обязательный bootstrap ([`../metamodel/08-field-expansion.md`](../metamodel/08-field-expansion.md), раздел 8, п. 6).
2. Состав полей экземпляра не виден в «голом» Markdown: требуется вычисление плагином или валидатором (как и для INV-20). Компенсация: алгоритм задокументирован, предупреждения о неактивных полях — фаза 2.
3. Реестр свойств ядра вырос с 15 до 23 записей, ориентир 10–18 (TASK.md iter-005) превышен. Компенсация: восемь новых записей — три триггера и пять полей, необходимых им (TASK.md iter-006: «только 3 триггера и необходимые им поля»); каждое дальнейшее свойство — через DL.
4. Правило может сослаться на ключ определения, которое позже переведено в `deprecated`: поле перестанет быть действительным. Компенсация: INV-25 требует существования определений, проверка — при сохранении правила и правилом валидации фазы 2.
5. Осиротевшие значения накапливаются: владелец может годами не чистить неактивные поля. Компенсация: предупреждения валидации и явная команда очистки (контракт, раздел 8, п. 2–3).
