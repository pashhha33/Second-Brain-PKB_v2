# ADR-010: Фаза 2 — состав второй волны JSON Schema: значения фасетов и формы значений свойств ядра

Архитектурное решение о второй волне схем `schema/`: какие классы объектов и формы значений получают машиночитаемое выражение, как схема соотносится с реестрами фазы 1 и с границей «схема — правило», что сознательно отложено.

## Контекст

1. Первая волна (ADR-009, S4) оставила вне схем: значения фасетов (`type: facet-value`, ключ `facet`), определения `automation`, свойства ядра и специфичные формы их значений, экземпляры типов слоя наполнения, схему всего vault. В iter-010 класс объектов `system-definitions.json` расширен объектом `type: validation-rule` (DL-041). Критерий успеха фазы 2 при этом требует, чтобы каждый инвариант и реестровое ограничение имели JSON Schema или правило валидации.
2. **Форма значения по `value_type` — часть INV-21 без машиночитаемого выражения.** Схема контролирует `value_type` в определении (набор из 14 значений) и наличие `enum_values`, но не форму значения в данных: дата как строка ISO 8601, `media` как ссылка с префиксом `image_`, `list<enum>` как список, а не скаляр. Проверка «форма значения по `value_type`» перечислена кандидатом **третьей волны правил** ([`../validation/00-validation-rules.md`](../validation/00-validation-rules.md), раздел 7), тогда как по границе ADR-009 (S1.1) это форма одного объекта — территория схемы, а не правила.
3. **Значение фасета — класс объектов с обязательным служебным ключом, не покрытый схемой.** Ключ `facet` (`link`, `always`, `applies_to: facet-value`, кратность `1..1`) нормативен в [`../metamodel/04-properties.md`](../metamodel/04-properties.md), раздел 6; в реестре служебных ключей определений (раздел 5) его нет, потому что он относится к слою классификации, а не к определениям системного слоя.
4. **Свойств ядра 23** ([`../metamodel/07-core-properties.md`](../metamodel/07-core-properties.md)), формы их значений различаются (`media`, `list<media>`, `string`, `text`, `date`, `number`, `list<string>`, `enum`, `list<enum>`). Полный перенос всех ключей и их `enum_values` в схемы противоречил бы DL-037, Q-005 и пункту 2 раздела 8 реестра правил; TASK.md iter-011 ограничивает волну «обоснованным минимумом» (5–12 свойств) и прямо исключает полный перенос `enum_values`.
5. **Экземпляр схемы — документ из YAML frontmatter одной заметки** (ADR-009, S2): состав полей экземпляра вычисляется по типу, цепочке `extends` и активным правилам развёртывания (INV-20, INV-26), `additionalProperties` не запрещён (S2.4). Следовательно, схема ключей свойств не может ни перечислить допустимый состав полей объекта, ни проверить соответствие ключа области применения `applies_to` — это вычисление и правило, а не схема (S1.4).
6. Ограничения итерации: существующие схемы не ломаются (точные `$ref` и правки согласованности), версия — JSON Schema 2020-12, `examples/`, `plugin/`, CI и исполняемый валидатор вне scope.

## Решение

### W1. Состав второй волны схем

| Файл | Класс объектов / документа | Проверяет | Основание |
|---|---|---|---|
| [`../../schema/facet-value.json`](../../schema/facet-value.json) | объект `type: facet-value` (слой классификации) | восемь обязательных свойств через `$ref` на `object.json`; `type: facet-value`; `layer: classification`; обязательный ключ `facet` — каноническая ссылка с префиксом `facet_` и alias; одиночная форма значения (кратность `1..1`) | INV-09, INV-12, INV-15; [`../metamodel/04-properties.md`](../metamodel/04-properties.md), раздел 6; [`../metamodel/03-builtin-types.md`](../metamodel/03-builtin-types.md), раздел 9; [`../metamodel/02-layers.md`](../metamodel/02-layers.md) |
| [`../../schema/core-property-values.json`](../../schema/core-property-values.json) | формы значений и двенадцать ключей свойств ядра (фрагмент документа frontmatter) | `$defs` по каждому из 14 значений `value_type` (`string-value`, `text-value`, `number-value`, `integer-value`, `boolean-value`, `date-value`, `datetime-value`, `enum-value`, `list-of-string`, `list-of-enum`, `link-value`, `list-of-link`, `uuid-value`, `media-value`, `list-of-media`); форма значений 12 ключей: `cover`, `poster`, `photo`, `artwork`, `url`, `isbn`, `published`, `attachment`, `position`, `occupation`, `format`, `creation-method` | INV-21, INV-23; [`../metamodel/04-properties.md`](../metamodel/04-properties.md), раздел 2; [`../metamodel/07-core-properties.md`](../metamodel/07-core-properties.md), разделы 1–3; ADR-009 (S2.3) |

Отложено (осознанно, без изменения статуса в ADR-009, S6): определения `automation` (состав ключей моделью не определён, термин в глоссарии — черновик); остальные одиннадцать ключей свойств ядра (`year`, `duration`, `date`, `due`, `completed`, `page`, `specialization`, `model`, `prompt`, `seed`, `page-count`) — формы для них уже есть в `$defs`, перенос ключей не требует новых форм; значения ключей отношений (`parent`, `part-of`, `chapter-of`, `object-facet-value` и остальные) — форма ссылки уже выражена `object.json#/$defs/canonical-link`, а соответствие кратности (`0..1` — одиночная ссылка, `0..*` — список) остаётся кандидатом третьей волны правил; экземпляры типов слоя наполнения (состав полей вычисляется, INV-20); схема всего vault как единого документа (ADR-009, А5).

### W2. Раскладка: один файл — один класс объектов

`facet-value.json` и `core-property-values.json` — отдельные файлы (ADR-009, S3.3; R-004). Ветки в `system-definitions.json` не добавляются: класс объектов этого файла — определения и правила **системного слоя**, а значение фасета является экземпляром слоя **классификации**. Прецедент DL-041 (объект `validation-rule` пятой ветвью) не переносится на `facet-value`: правило валидации — объект системного слоя, определённое встроенным метатипом, то есть принадлежит тому же классу, что и остальные ветви файла. Образец для экземпляра отдельного класса — `media.json` (обёртка `image`, слой наполнения). `core-property-values.json` описывает не класс объектов, а формы значений, поэтому отдельный файл сохраняет `object.json` как схему универсальных обязательных свойств любого объекта.

### W3. Форма значения — схема, набор значений — реестр

Схема фиксирует **форму** значения по `value_type`: скаляр или список, строка ISO 8601 для `date` и `datetime`, число для `number`, каноническая ссылка для `link` и `media`, «сырой» UUIDv7 для `uuid`. Наборы `enum_values` конкретных свойств в схему не переносятся: источник нормы — [`../metamodel/07-core-properties.md`](../metamodel/07-core-properties.md) и определения свойств (ADR-009, S6, пункт 2; DL-037; Q-005; [`../validation/00-validation-rules.md`](../validation/00-validation-rules.md), раздел 8, пункт 2). Основание: набор `enum_values` расширяем владельцем без DL ([`../metamodel/04-properties.md`](../metamodel/04-properties.md), раздел 2, правило 4), поэтому закодированный в схеме набор устаревал бы при каждом расширении и отвергал допустимые данные. Принадлежность значения набору — правило третьей волны, а не схема.

### W4. Частичная схема документа (фрагмент)

Корень `core-property-values.json` — `type: object` с `properties` двенадцати ключей и без `additionalProperties`: схема проверяет форму значения перечисленных ключей **если ключ присутствует** и применяется вместе со схемой класса объекта (`object.json`, `system-definitions.json`, `media.json`, `facet-value.json` — выбор схемы по значению `type`, ADR-009, S3.4). Соответствие ключа области применения его определения (`applies_to`) и эффективный набор полей не проверяются: это вычисление (INV-20, INV-26, ADR-009, S1.4) и кандидат третьей волны правил.

### W5. Сужения формы — только по явному указанию реестра

Сужение `number` до `integer` и ограничение `minimum: 1` введены для `position`: реестр фиксирует «порядковый номер … нумерация с 1, пропуски допустимы» ([`../metamodel/07-core-properties.md`](../metamodel/07-core-properties.md), раздел 3, пункт 2). Для `duration`, `seed`, `page-count` и `year` оставлена общая форма `number-value`: реестр называет единицы измерения (минуты, страницы), но не фиксирует целочисленность и диапазон, а ограничение, которого нет в принятом тексте, схема вводить не должна. Паттерны для `isbn` и `url` не вводились по тому же основанию: реестр описывает их как `string` (раздел 3, пункты 3 и 6).

### W6. `defined_by` не фиксируется `const`

Схема значения фасета требует, чтобы `defined_by` был UUIDv7 (`object.json#/$defs/uuidv7`), но не фиксирует `id` встроенного метатипа 9 как константу: форма совпадает с `media.json` и `system-definitions.json`, где `defined_by` также не константа, а согласованность `defined_by` и `type` проверяет правило первой волны `defined-by-consistent` (INV-12, INV-13), неизменяемость встроенных метатипов защищает INV-14. Дублирование проверки правила схемой противоречило бы ADR-009 (S1.3) в обратную сторону: константа в схеме сделала бы правило избыточным для одного класса объектов и не отменила бы его для остальных.

### W7. Правки существующих схем — точечные

`system-definitions.json`: предложение о значениях фасетов в `description` заменено указанием на `facet-value.json` (состав проверок не менялся). `media.json`: `description` у `$defs/media-value` уточнён — форма-объединение используется, когда `value_type` не определён статически, а схемы ключей ссылаются на точные формы `media-link` и `list-of-media-links`. `object.json` не менялся. Ни одна проверка первой волны не изменена и не удалена.

## Альтернативы

### А1. Раскладка форм значений свойств ядра

| Вариант | Почему отклонён |
|---|---|
| Файл на каждое свойство ядра (`property-cover.json` и ещё 22) | 23 файла при одинаковом содержании: форма значения определяется `value_type`, а не ключом; изменение формы потребовало бы правки всех файлов |
| `$defs` форм значений внутри `object.json` | Класс `object.json` — универсальные обязательные свойства **любого** объекта; формы значений свойств ядра относятся к экземплярам и к реестру фазы 1 (смешение классов, R-004, ADR-009, S3.3), а файл вырос бы втрое |
| Блок или ветвь в `system-definitions.json` | Класс файла — определения и правила системного слоя; значения свойств хранятся в экземплярах слоя наполнения |
| Не создавать схему, выразить форму значения правилом третьей волны | Нарушило бы ADR-009 (S1.3): проверка формы одного объекта выразима схемой, а правило дороже, требует исполнения плагином и дублировало бы схему |
| Схемы по типам (`book.json`, `person.json`, `image.json` …) | 29 файлов, состав полей каждого вычисляется по INV-20 (цепочка `extends`, `excludes`, правила развёртывания), поэтому схема типа дублировала бы вычисление и устаревала при каждом правиле развёртывания |
| Один файл `core-property-values.json` с `$defs` форм и `properties` 12 ключей | **Принят**: один класс («формы значений и ключи свойств ядра»), `$defs` переиспользуются будущими схемами, объём — 128 строк |

### А2. Место схемы значения фасета

| Вариант | Почему отклонён / принят |
|---|---|
| Шестая ветвь `oneOf` в `system-definitions.json` | Класс файла — определения системного слоя; `facet-value` — экземпляр слоя классификации, ветвь сделала бы выбор схемы по `type` неоднозначным (ADR-009, S3.4) и расширила бы расхождение с S4, уже отмеченное DL-041 |
| Общий `classification.json` с ветвями `domain`, `hierarchical-category`, `facet`, `facet-value` | Вне объёма итерации: TASK.md ограничивает волну значением фасета, а состав ключей домена, категории и фасета схемой не описан. Слияние четырёх классов в один файл возможно позже через DL при переносе остальных классов |
| `$defs` в `object.json` | Смешение классов (см. А1) |
| Отдельный `facet-value.json` | **Принят**: один файл — один класс объектов (ADR-009, S3.3), образец — `media.json` для обёртки `image` |

### А3. Наборы `enum_values` свойств-триггеров

| Вариант | Почему отклонён / принят |
|---|---|
| Закодировать наборы `occupation`, `format`, `creation-method` в схеме | Набор расширяем владельцем без DL (раздел 2, правило 4 `04-properties.md`): схема отвергала бы допустимые после расширения данные; противоречит DL-037, Q-005 и разделу 8, пункту 2 реестра правил |
| Закодировать с пометкой «стартовый набор» | Две точки нормы на один набор — прямой путь к рассинхронизации (риск ADR-009 «канонические наборы продублированы») |
| Не кодировать наборы, фиксировать только форму (скаляр / список непустых строк) | **Принято**: форма — территория схемы (W3), принадлежность значения набору — правило третьей волны |

### А4. `additionalProperties` во фрагменте схемы

| Вариант | Почему отклонён / принят |
|---|---|
| `additionalProperties: false` | Фрагмент отверг бы любой объект с другими ключами, а состав полей вычисляется (INV-20, INV-26) и не хранится в схеме (ADR-009, S2.4) |
| `unevaluatedProperties: false` | Требует применять все схемы к одному документу одновременно, что несовместимо с выбором схемы по значению `type` (ADR-009, S3.4) |
| Не ограничивать | **Принято**: схема проверяет форму перечисленных ключей и не высказывается об остальных |

### А5. Сужения числовых и строковых форм

| Вариант | Почему отклонён / принят |
|---|---|
| `integer` и диапазоны для всех свойств с `value_type: number` | Реестр не фиксирует целочисленность `duration`, `seed`, `page-count`: схема ввела бы ограничение, которого нет в принятом тексте |
| Паттерны для `isbn` и `url` | Реестр описывает оба как `string`; формат ISBN (10 или 13 символов, дефисы) и форма URL моделью не нормализуются — паттерн отверг бы допустимые данные |
| Сужать только там, где реестр фиксирует ограничение явно | **Принято**: `position` — «нумерация с 1» (W5); `year` («год четырьмя цифрами») переносится вместе с ключом в следующей волне |

### А6. Объём волны

| Вариант | Почему отклонён / принят |
|---|---|
| Все 23 свойства ядра | TASK.md iter-011 ограничивает волну обоснованным минимумом (5–12); одиннадцать ключей не добавляют новых форм значений — их перенос не требует решения и выполняется точечно |
| Только формы значений, без ключей | Формы без привязки к ключам не проверяли бы ничего: экземпляр схемы — документ frontmatter, а соответствие «ключ → `value_type`» и есть переносимое знание |
| Двенадцать ключей, покрывающих все формы, которые встречаются в реестре свойств ядра, кроме `text` и `list<string>` | **Принято**: `media`, `list<media>`, `string`, `date`, `number` (сужение `integer`), `enum`, `list<enum>` представлены ключами; `text`, `list<string>`, `boolean`, `datetime`, `link`, `list<link>`, `uuid` — в `$defs` для переиспользования |

## Последствия

**Положительные:**

1. INV-21 получил машиночитаемое выражение в части формы значения: для двенадцати ключей свойств ядра и для всех 14 `value_type` в `$defs`. Проверка «форма значения по `value_type`» перестала быть исключительно кандидатом третьей волны правил.
2. Значение фасета — объект с обязательным ключом `facet` — проверяется схемой: состав объектов модели, имеющих собственный обязательный ключ, закрыт (`image` — `media.json`, `facet-value` — `facet-value.json`).
3. Каталог `schema/` остаётся автономным: относительные `$id`, межфайловые `$ref` по именам файлов и указателям `#/$defs/…`, внешних URL кроме идентификатора версии нет; формы `link`, `media`, `uuid` и непустой строки не продублированы, а подключены через `$ref` на `object.json` и `media.json`.
4. Граница «схема — правило» сохранена: схема не проверяет существование цели ссылки, уникальность ключей, `applies_to` и эффективный набор полей — эти проверки остаются правилами (первая, вторая и третья волны).
5. `$defs` форм значений переиспользуются: перенос остальных одиннадцати ключей свойств ядра, ключей отношений и схем экземпляров не требует новых форм, только ссылок.

**Риски и компенсации:**

| Риск | Компенсация |
